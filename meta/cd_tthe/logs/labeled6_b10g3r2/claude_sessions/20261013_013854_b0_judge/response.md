Reviewing traces of the three 100% candidates (all three have the model write its own queries) to compare their robustness.I chose **`cand_labeled6_b10g3r2_b0r1g2`** and wrote that name to `choice_b0.txt`.

- **No candidate breaks the interface.** I read all three that scored 100% (`b0r0g2`, `b0r1g2`, `b0r1g0`). In each, the model writes every query. The harness only rejects a reply and asks again, and if the model never gives an acceptable query, the harness sends the model's own last one.
- **`b0r1g0` is the weakest of the three.** It only blocks queries the model has already asked or that the rules already decide. That happened 35 times across its 10 traces, which shows the model still wanders. It also leaves any undecided rows of the final answer for the model to fill in.
- **`b0r0g2` and `b0r1g2` share the same core.** From the inventory and circuit rules alone, they list every possible set of three circuits that fits. After each answer they drop the ones that no longer fit and show the model what is still possible. They stop as soon as only one fits, and a final answer that contradicts the evidence is sent back. In every episode for both, only one possibility remained at the end, so the model was copying a fully determined answer.
- **Why `b0r1g2` over `b0r0g2`:** it adds one general safeguard. It rejects a query that would split the remaining possibilities less evenly than the best available one and asks the model again. That rule protects against episodes on larger rule spaces where 18 queries don't narrow things to one answer. Its own notes give a 2–18% rate for that without the rule; I didn't re-run anything to check that figure. The rule rarely needed to act on this batch (2 times in 10 episodes), and it used slightly fewer queries per episode (11.6 vs 12.0).
- **Trade-off:** that same rule steers the model more firmly. When only one query is best, the model is pushed to pick exactly that one. This is still allowed, because the model writes the query and the fallback is the model's own choice.
