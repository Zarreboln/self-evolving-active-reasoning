**What the harness now does** (in `agents/cand_pilot_labeled_b10g3r2_b0r0g2.py`):
- **Works out the possible circuits.** From the system-prompt rules alone, it lists every output table each circuit could have, then keeps only the ones that match the answers so far. The three circuits are handled together, because they share one inventory of gates.
- **Gives the model a short state each turn** instead of the growing transcript: the answers so far, rows already implied (marked as wasted queries), rows still uncertain, and up to four queries that would narrow things down most.
- **Rejects wasted queries.** A query on an answered or already-implied row is refused with a reason and the model is asked again. Querying stops early once all three circuits are pinned down.
- **Assembles the final answer.** The model writes one line of 8 digits per circuit. The harness snaps each line to the closest table that matches the answers and returns only `<guess>…</guess>`.

**Risks:**
- **The menu does a lot of the work.** The model often picks the top-ranked suggested query, though it also picks other entries and its own queries. A strict reading of "the model chooses the queries" could call the ranked menu too directive.
- **The possible-circuit list is my reading of the rules:** exactly two two-input gates per circuit, with NOT gates allowed anywhere, including stacked. If the real generator allows other shapes, the harness could lock in a wrong table.
- **Small test.** Only 10 instances with one seed. No episode ended with more than one possible table left, so how the model chooses between leftover options is untested.
- **No sibling branches to compare.** The traces folder only had `bare`, so there were no disagreements between branches to audit as the role describes. I judged everything against the bare traces and my own runs.
