The new harness, `agents/cand_pilot_strict_b10g3r2_b1r1g1.py`, ran on all 10 instances without crashing, and `audit.py` passes it. On this batch it returns the same final table as the parent for every instance. The gain is in how efficiently the queries narrow down the circuits, so it should only change outcomes on harder gate inventories.

**Where I think episodes go wrong.** Every circuit has exactly two 2-input gates, and when I replayed the queries and answers against that rule, every branch ended with exactly one consistent set of three tables. None of the parent's roughly 50 check queries contradicted that reading. So the remaining risk is running out of queries before the circuits are fully determined. The parent ranks each candidate query by how evenly it splits one circuit's possible tables, and offers the model 8 of them. That ignores the link between circuits: they share the gate inventory, so one circuit's answers rule out options for the others. The parent sent 3 queries whose answers were already fixed by that link, and instances 209 and 236 used 15 of the 18 queries just to pin the circuits down.

**The change.** The harness now lists every combination of tables for A, B and C still allowed by the rules and the answers so far. It ranks each query by how evenly it splits those combinations and shows the model only the best 3. If the model picks something else it is asked again, and any useful query is accepted on the last try. The model still writes every query. If there are too many combinations to list (over 300k, which happens with 4 or more NOT gates) or an answer contradicts the rules, the parent's ranking is used unchanged. Everything else from the parent is kept, including the check queries once all circuits are known.

**What the re-run showed** (from the traces only):
- **Information per query:** about 0.89 bits per query on average before the circuits were pinned, against 0.82–0.84 for the parent and both sibling branches. No query was wasted, compared with 3 for the parent.
- **Queries to pin the circuits:** mean 10.9 (worst 14), against 11.4 (worst 15) for the parent. This number depends on how the answers happen to fall, and two instances got worse: 130 (9 vs 6) and 228 (13 vs 10). In 228 it still went from 3924 possibilities to 1 in 13 queries, against a theoretical minimum of 12.
- **Model's choices:** it picked the 1st, 2nd and 3rd menu item 50, 15 and 44 times, and never anything outside the menu. Because the options are usually close, this costs only about 0.017 bits per query.
- **Simulation:** I sampled 150 random rule-consistent circuit sets per inventory and had a simulated player pick at random from each menu. With 3 NOT gates, the parent's 8-option menu needed more than 18 queries to pin the circuits in 33 of 150 cases, against 5 of 150 for the new 3-option menu. With 0–2 NOT gates, neither ran over in any case except one inventory, where the parent ran over in 2 cases.
