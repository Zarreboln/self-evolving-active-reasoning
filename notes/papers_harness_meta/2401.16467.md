## 任务

LLM 程序合成:给一个 query,LLM 生成一段程序,执行后得到答案。五个数据集:LOGO(turtle 画图,程序归纳)、Date(BBH 日期推理)、TextCraft(Minecraft 合成的文本游戏,但被改成**一次性生成整段 Python**,不接受逐步环境反馈)、MATH Algebra level 1–2、TabMWP level 1–4(§4.1,Table 5)。训练数据是 (query, 原语程序) 对,每个数据集约 66–200 条(Table 5)。

## 问题

逐题独立生成程序有两个缺陷(§1):"Lack of Reusability"(同样的子程序每次重写,一次写对另一次写错)和 "Lack of Abstraction"(只用原语时模型要自己把 query 映射到多个原语,推理负担重)。作者认为根源是 "a lack of global context as the model sees each example separately"。同时要权衡过拟合:`draw_9gon_snowflake()` 只匹配一个例子,`draw_small_9gon()` 才通用(§1)。

## 方法

- **两阶段**(§3,Fig. 2,Algorithm 1/2):训练阶段(induction)从 (q, p) 学出 **Code Bank C**(helper 函数库)和 **Demo Bank D**(用了 helper 的重构后程序,作使用示例);测试阶段 agent 检索 C 和 D 来写新程序。训练是 gradient-free,refactoring LLM 冻结(GPT-3.5)。
- **预处理**(§3.1,A.1):(可选)让 GPT-3.5 给原语程序加注释,先把 query 分解再按分解注释,注释后程序须与原程序 exact match 或执行结果一致;用 OpenAI Ada 嵌入 query,**Ward 层次聚类**得到一棵树,拓扑排序后切成大小 k 的 batch("multi-instance scope");按 query 平均长度排 curriculum,短的在前。
- **Stage 1 refactorBatch**:一次给 LLM 一个 batch 的 (q, p) 加当前 C,要求写新 helper 并重写每个程序,"MUST execute to the same result as the original programs","Try to make your new programs as short as possible by introducing shared helper functions"(Table 10 prompt)。
- **Stage 2a verify**:执行重构程序,要求 p̂() = p()。只有通过验证的 helper 才进 C;通过的重构程序进 D;失败记录保留给 edit/prune 用(§3.2)。
- **Stage 2b retry**:失败的程序连同报错/输出再给 LLM 重写一次(LOGO 输出是图片,不给)。
- **Stage 3a editCodeBank**:每 editEvery 个 batch,对每个函数展示通过和失败的单元测试(即用到它的 demo),CoT 先解释为什么失败再给新版本;**新版本通过的测试更多才替换**;签名变了就用 prompt 改单元测试(§3.2,A.2,Table 13)。prompt 里明确鼓励 "add parameters instead of hardcoded values or call other helper functions"。
- **Stage 3b pruneCodeBank**:每个函数打分 s = |P| − Σ_{p∈F} 1/n_p(P 通过的程序,F 失败的程序,n_p 为该失败程序用到的函数数,失败责任按函数数平摊);用过足够次数且 s < θ(所有实验 θ=0)就删(A.2)。测试前再 prune 一次(A.3;但 Table 9 里 TextCraft 的 "Filter before testing" 是 False)。
- **测试 agent**(§3.3,A.3,Algorithm 2):ICL 预算 10 条,按比例 r(全部 0.5)分给 Demo Bank 示例和原始训练集的原语程序;另外按 query 与函数名(及描述)的相似度检索 ≤20 个 helper 放进 prompt;ChromaDB + Ada 嵌入。加 ReAct 式 "thought" 让模型先想用哪些函数,脚注 4:"Without these additional 'thought' statements, we found the augmented agent rarely uses any helper functions."

## 对照问题 a–j

**a. 学到/共享的是什么?**
一个 **Python helper 函数库(Code Bank)** 加一个 **使用示例库(Demo Bank)**。helper 是真代码、可执行、可单测;Demo Bank 是重构后通过验证的 (q, p̂),测试时作为 ICL 示例,同时在训练中充当每个函数的单元测试(§3.2,A.2)。共享只在**单个数据集内部**:每个域各学一个库(§4.1,§5),没有跨域库。作者把它比作 "learning a DSL on top of an extremely general set of primitives"(§7)和 HRL 的 option discovery(§7)。

**b. 库的结构?**
**扁平**。C 就是一个函数集合,没有层级、类别、成员关系或父子关系。函数之间唯一的关系是可以互相调用:refactor prompt 把现有 C 的定义给模型选用(Table 10),edit prompt 鼓励 "call other helper functions"(Table 13);但论文没有把调用关系当结构建模,也没报告库里有多少层组合。**层次聚类(Ward)只用于预处理时组 batch 和排 curriculum**(§3.1),不进入库的结构,测试时也不用。测试时按 query 与函数名/描述的嵌入相似度取 top-20(A.3)。库有多大(函数个数)论文**未报告**。

**c. 程序怎样拆成 helper?**
不是"拆一个程序",而是**对一批相关程序同时做 refactoring**:LLM 看 k 个(3–5,Table 9)query 相近的原语程序,提出共享 helper 并改写每个程序,目标是变短("as short as possible")且执行结果不变。保证正确的手段是**执行等价验证** p̂() = p(),只有验证通过的 helper 入库;失败的带报错 retry 一次;周期性 edit(按单测通过数择优替换)和 prune(按 s = |P| − Σ1/n_p 打分,θ=0)(§3.2,A.2)。注意入库门槛是"至少一个通过验证的重构程序用到它",**没有"必须被 ≥2 个例子使用"的硬约束**;泛化性靠 batch 级多实例 refactor、编辑提示里的参数化要求、以及失败多就被 prune 间接保证。

**d. held-out 是任务还是实例?**
主实验全部是**同数据集内的 held-out 实例**(Table 5 的 train/dev/test)。唯一接近"新任务"的是 §6.4 / Table 4:TextCraft 里**目标物体类别未见过**(test 要做 fence,train 没有 fence),仍是同一游戏、同一原语。没有跨数据集或跨任务族的 held-out:LOGO 学的库不拿去做 TextCraft。

**e. 迁移 / 负迁移有没有测?**
没有跨域迁移实验,也没有库 × 任务矩阵。**跨模型**算一种迁移:GPT-3.5 训练出的库给 5 个不同 agent 用(Table 1),作者在 related work 强调 "a shared code bank that can be used by multiple LLMs"。负效应在 Table 1 里实际出现但**正文没有当负迁移分析**:CodeLlama-13B TabMWP 29.1→27.9,Lemur-70B MATH 14.0→13.1、TabMWP 27.5→25.7,CodeLlama-7B LOGO 不变;作者对 Lemur 的解释是空输出多、"roughly comparable"(§5)。§6.2 的 13 个反例(多数是 connector code 写错)是唯一的定性"为什么有害"分析,归因于 ICL 预算被分走。什么因素预测有无收益:只在 §7 Limitations 定性说 "not every domain has reusable abstractions… the primitives for a domain may already be suitably abstract"。

**f. 模型、预算、成本?**
- Refactoring(训练)模型:GPT-3.5(gpt-3.5-turbo-0613,A.4);注释也是 GPT-3.5;MATH 的银标程序用 GPT-4 + PoT 生成;Date 的银标程序来自 Lyu et al. 的 GPT-3.5 预测;TextCraft 的原语程序由 ADaPT 轨迹规则翻译得到(A.5)。
- 测试 agent:CodeLlama-7B/13B/34B-Instruct、Lemur-70B-v1、GPT-3.5-turbo。
- 超参(Table 9,只给了 LOGO / Date / TextCraft;**MATH 和 TabMWP 的超参未列出**):refactor 轮数 3/1/1,editEvery=pruneEvery=5,batch 5/3/4,θ=0,ICL 比例 0.5。
- 训练数据 66–200 条。
- **没有报告训练的 API 调用次数、token、美元成本或墙钟时间**,也没报告测试 prompt 变长的代价。§7 只有一段定性论述 "convert a variable cost… into the fixed cost of running ReGAL"。

**g. Baselines 与主数字**
主要 baseline 是**同数据、同 ICL 预算(10 条)、同 prompt 但没有 helper 的原语 agent**(§4.2,Table 14 说明两者 prompt 相同,只是 codebank_str 为空)。外部 baseline 只有 LILO、Faithful-CoT、ReAct(Table 2),且作者承认不可比。**没有和 DreamCoder、CRAFT、CREATOR、TroVE、LATM、Voyager 直接对比**,只在 related work 里讨论。主数字见"结果"一节。

**h. 泄漏/过拟合控制**
- 用 dev 选超参(§3.2 末:"We use the dev set to select hyperparameter values"),消融也在 dev 上做(Table 3)。
- 验证用的是**训练集的 gold/银标程序执行结果**,不碰 test。
- MATH/TabMWP 训练只用正确程序,dev/test 正确和错误样本都用(§4.1)。
- 过拟合讨论集中在"函数过于特化"上(`draw_9gon_snowflake`),靠 edit/prune 处理;Table 4 显示在偏移下 prune 带来 +3.5。
- 有一个值得注意的点:Date 的 train/dev/test 都从 Lyu et al. 的 GPT-3.5 预测里切出来(§4.1),train 按正确性过滤;baseline 和 ReGAL 共用这批程序作 ICL,所以对两者公平,但论文没讨论 GPT-3.5 自产程序再给 GPT-3.5 用的问题。
- 测试有 3 个随机种子并报标准误(Table 1);**refactoring 训练本身是否多次重复、库的方差多大,论文未说明**。
- 没有讨论 reward hacking(验证是执行等价,作弊空间小)。§6.2 报告了 2 例验证器假阴性。

**i. 代码/数据**
GitHub 公开(见页首)。README:LOGO、Date 的预处理和训练脚本;评测脚本只有 CodeLlama-13B;TextCraft "coming soon"(截至最后 push 仍如此);MATH/TabMWP 未提。论文说发布了改写成 Python 的 LOGO 数据(§4.1)。学到的 Code Bank 是否单独发布,README 只说训练后在 `logs` 里,论文未说明。

**j. 自述局限**
§7 Limitations:(1) 函数是代码,不如神经网络参数化的模块灵活,在环境动态变化的域(如导航)可能学不到函数,"verification-based pruning means that no functions would be discovered in these cases";(2) "not every domain has reusable abstractions, and not every example stands to benefit from them",原语可能本来就够抽象;(3) "ReGAL's abstractions are not necessarily the same as those a human would choose"(B.1)。另在 §6.2 承认共享 ICL 预算导致 connector code 错误。没有列 future work 清单。

## 与我们的区别

我们的方法:把完整 agent harness(冻结 LLM 外的 prompts、memory、control flow、parsing 代码)按任务逐个摄入,经过质量门(须明显胜过 base agent),由 Opus 写任务描述/能力/画像和 harness 描述,再由一次 "review" 把共享功能提炼成 `module` 和 `workflow` 节点,节点组成多父 DAG(soft hierarchy),每个节点有真代码、描述、父节点、成员任务及可核对证据(函数名或 ≥40 字原文摘录),节点至少 2 个成员任务;新任务先探 3 题、描述、按嵌入相似度检索相似任务和节点、优先复用来组合首个 harness,再由 Opus 看轨迹做少量编辑。计划加设计者侧经验条目(when/provide/use)和扁平/两层/单继承树/soft hierarchy 的消融。冻结 Qwen3.5-9B 玩文本游戏。

**ReGAL 已经做了的(重叠,直说)**
1. **"从已有程序里用 LLM 提炼可复用代码库,新问题检索库来组合"这个核心范式,ReGAL 已经做了,而且是 ICML 正会**。我们的 review 提炼 module 节点,和 refactorBatch 提炼 helper 函数是同一个动作;我们按嵌入检索节点,和他们按 query–函数名相似度取 top-20 是同一个动作。
2. **库里存真代码 + 使用示例**:他们 Code Bank + Demo Bank,我们节点代码 + 成员证据(函数名/摘录)。结构上很像。
3. **多实例 scope 才能提共享抽象**:他们明确要求 batch 内是相关程序("multi-instance scope"),我们要求节点 ≥2 个成员任务,动机相同。
4. **用 embedding 聚类/相似度组织相关项**:他们用 Ward 层次聚类组 batch,我们用相似度找相似任务。
5. **文本游戏 + 冻结小开源模型受益**:TextCraft 是文本游戏,CodeLlama-13B 受益最大且超过 GPT-3.5。我们的"冻结 9B 用共享 harness 代码变强"在叙事上与此重合。
6. **新数据到来后继续更新库**:Table 4 在 unseen dev 上再 prune/再训练一轮,和我们"新任务摄入后更新层级"相近。
7. **库的维护机制(edit 择优替换、按失败归责 prune)**比我们目前的设计更完整:我们只有入库门槛(≥2 成员 + 证据),没有基于使用结果的删改。

**ReGAL 没做的(我们的空间)**
1. **抽象单位不同**:ReGAL 抽象的是单次生成的短程序(LOGO 图形、日期运算、合成步骤),agent 每题生成一段程序就结束,TextCraft 甚至被刻意改成无环境反馈的一次性程序。我们抽象的是**多轮交互的整套 harness**(prompt、记忆、控制流、解析),被复用的是"agent 怎么搭",不是"答案程序里的子例程"。ReGAL 里根本没有 workflow 层(怎样把模块组装成 agent 循环)。
2. **库结构**:ReGAL 是扁平函数集,层次聚类只用于排 batch。我们是多父 DAG,有 module/workflow 两类节点和显式成员关系。扁平 vs 层级 vs soft hierarchy 的问题 ReGAL 完全没有碰。
3. **跨任务/跨域**:ReGAL 每个数据集一个库,held-out 只是同数据集的实例(最多是 TextCraft 的未见物体类别)。我们的库跨 Wordle/Hangman/BabyAI/SciWorld/DC,测试是**未见任务**(Mastermind、Minesweeper、ALFWorld、Twenty Questions 等)。
4. **来源异质**:ReGAL 的输入是同一 DSL 下格式统一的 (q, p) 对;我们的输入是来源不同(Meta-Harness 进化 / 人写)、结构差异很大的完整 harness,外加质量门。
5. **新任务流程**:ReGAL 测试时只是检索 + 一次生成;我们有探测、描述、组合首个 harness、再按轨迹编辑。
6. **设计者侧经验**(when/provide/use,含失败版本历史):ReGAL 没有;它只保存最终通过验证的代码,失败记录只用于 edit/prune 打分。

**审稿人可能的攻击与应对**
- **"这就是把 ReGAL(以及 LILO、TroVE、CRAFT)搬到 harness 层面。"** 应对:正面承认库学习范式继承自 ReGAL 一系,把贡献明确放在 (i) 抽象对象是多轮 agent harness 而非单次程序,带来 workflow 层,(ii) 跨任务族的 soft hierarchy,(iii) 未见任务上的组合。最好直接跑一个 **"ReGAL 式扁平库"baseline**:同样的 harness 来源,refactor 成扁平函数集,按相似度 top-k 检索。这正好就是我们计划的 flat library 消融,应在论文里写明它对应 ReGAL。
- **"你们的节点代码没有执行验证。"** 这是最实在的一刀。ReGAL 每个 helper 都要执行等价 p̂()=p() 才入库,我们的证据是文本层面的(函数名、≥40 字摘录),只证明"这段功能在该任务 harness 里出现过",不证明"提炼后的节点代码在该任务上行为等价或可用"。应对:加一道执行检查,比如把成员任务的 harness 改写成调用节点代码,在少量题上回放,分数不低于原 harness 才算成员(相当于 ReGAL 的 verify);做不到就要在文中明说证据是 provenance 而不是 correctness。
- **"库没有维护机制,坏节点会一直留着。"** ReGAL 的 Table 3 显示 edit/prune 各贡献不小(去 prune 后 TextCraft 34.12→25.26)。应对:借用它的打分 s = |P| − Σ1/n_p,按新任务使用节点后的成败给节点归责,低分节点修改或降级。
- **"收益来自更多 ICL / 更长 prompt,而不是层级。"** ReGAL 用固定 10 条 ICL 预算来控制这个变量。应对:各消融条件之间控制检索到的节点数和注入 token 数,扁平/两层/树/soft hierarchy 用同样预算。
- **"层级会不会是多余的?"** ReGAL 的扁平库已经在 5 个域有效。应对:必须在未见任务上展示 soft hierarchy 胜过扁平库,并给出 workflow 节点被复用的统计(类似 Fig. 3 的调用次数图)。
- **"小模型用了库也可能变差。"** ReGAL 自己的 Table 1 有三处下降,§6.2 显示多数失败是 connector code 写错。可以引用作为 motivation:我们由 Opus 组合 harness,冻结 9B 不用自己写胶水代码,这一失败模式在设计上就被规避了(但要用数据证明)。

**结论**:ReGAL 已经做了"LLM 批量重构已有程序、提炼执行验证过的共享函数库、检索复用到新问题"这条主干,还带有 edit/prune 维护和跨模型使用,冻结的小开源模型在文本游戏上受益。我们在"库学习"这个层面没有新意,必须引用它并把扁平库消融明确定位为 ReGAL 式 baseline。我们真正不同的地方有四点:抽象对象是多轮 agent harness(因此有 workflow 层),库是跨任务族的多父 soft hierarchy,测试是未见任务而非同域实例,输入是来源异质、经过质量门的完整 harness。最大的方法弱点是节点缺少 ReGAL 那样的执行验证和基于使用结果的维护,这两点应该在投稿前补上。
