## 任务

给 tool-using LLM agent 预先建一个"即插即用"的技能知识库(SkillKB)。强模型(GLM-4.6)在训练任务上 rollout,把成功轨迹蒸馏成技能;测试时把检索到的技能一次性塞进较弱执行模型的 system prompt,ReAct 式执行。目标是式 (4):带技能的期望成功率高于不带技能(§2)。评测在 BFCL-v3(multi-turn base)、AppWorld、τ²-Bench(retail / airline / telecom)上做(§5.1)。

## 问题

作者认为现有 self-evolving agent 有三个结构性问题(§1):(1) Isolated Learning,每个 agent 对相同任务反复独立抽经验,冗余;(2) Weak Generalization of Experience,复杂环境训练数据少,抽出的经验迁移差;(3) Model Capability Bottleneck,靠自己探索得到的经验受限于自身能力上限。由此提的问题是 "What form of experience can be broadly reusable across agents of varying capabilities and across diverse environments?" 他们觉得 insight / workflow / trajectory 三种表示都不能同时做到"可迁移、好检索、直接可执行",而 Claude Skills 的长上下文渐进披露对推理和环境支持要求太高(Fig. 1)。

## 方法

- **三层技能**(§3.1 式 (5)):D = S_plan ⊕ S_func ⊕ S_atomic。
  - Atomic skill:对齐单个工具 t,是该工具 schema 的扩展说明(用法模式、典型参数、约束、常见失败)。
  - Functional skill:对应一个子任务的宏操作,"grounded in a set of tool actions",即工具组合 T_func ⊆ T。
  - Planning skill:子任务的组织结构(顺序、依赖、分支),"specifying how functional skills should be composed"。
  - Functional 与 atomic 用同一表示:`name / document / content / tools`(§3.2,附录 C.5、C.7)。content 是具体实现,在 AppWorld 里就是调用 `apis.*` 的 Python 风格片段(Fig. 2 例子、仓库 func_atomic_skills.json)。
- **抽取**(§3.2):每个训练任务 rollout m 次(实现中 m=4,温度 0.9;A.3)。只从**成功轨迹**抽。先把轨迹压成有序高层步骤作为 planning skill,显式滤掉探索、回溯、试错;环境反馈超过 1500 tokens 先摘要(A.3, C.2)。再以 plan 的每一步为单位抽 functional skill(C.7 "Specific-step guided extraction"),按工具抽 atomic skill(C.6)。抽取 prompt 给出现有库,模型对每条技能选 add / modify / keep。
- **迭代精炼**(§3.3 式 (6)(7)):D⁽⁰⁾=∅;第 k 轮用当前库 D⁽ᵏ⁾ 在训练集上 rollout → 抽取 → 精炼算子 φ(Merge + Filter)→ 更新得 D⁽ᵏ⁺¹⁾。最多 3 轮(§5.1)。
  - Merge:用 embedding 余弦相似度聚类(实现是 DBSCAN,阈值 0.9,每簇最多 15 条;A.3),然后交给 LLM 合并(C.5)。式 (9)(10) 把同簇邻居写成"更新方向 δ_i"并求和,但实际操作就是一个 merge prompt,式子是比喻。合并后的技能如果"overly complex"就 decompose 成更小的技能。
  - Filter 两段:General Filter(依赖额外 Python 包、过度特化、"thin wrapper" 的去掉;C.1);Tool-specific Filter(对照环境提供的 tool schema 检查不存在的工具、非法参数;C.3)。
- **探索扩展**(§3.4):统计种子 rollout 里哪些工具可靠、哪些常失败、哪些从没调用,引导 agent 去探索(每个训练任务 1 次,温度 1.0),从探索轨迹合成新任务 Q_syn,再跑一遍抽取与精炼。对照的是 AgentEvolver 的随机探索。
- **使用**(§4):先按任务相似度检索 planning skill,让执行模型自己改写出一个 pseudo-plan(HyDE 思路);pseudo-plan 本身**不注入** prompt,只当检索 query;按每一步检索 functional/atomic skill,去重,再让 LLM 自筛。检索用 Qwen3-Embedding-8B + FAISS HNSW,Top-100 粗召回,保留 cos≥0.45 且与最佳匹配差 ≤0.08 的,>0.95 近重复去重,MMR(λ=0.75)后最多返回 8 条(A.3)。检索到的 planning skill 本身是否注入 prompt,§4 没写清楚;Fig. 3a 有"只开 Planning Skills"的条件,推测是注入的。

## 对照问题 a–j

**a. 共享的是什么?NL 还是代码?给执行 agent 还是给 harness designer?**
共享的是**给执行 agent 读的技能条目**,一次性注入 system prompt(Fig. 1 "injected into the system prompt in one time")。条目是半结构化文本加代码片段:functional/atomic 有 `name / document / content / tools`,content 是调用环境 API 的 Python 风格片段(AppWorld 本身要求 agent 写代码,所以片段可被模仿);planning skill 是 "# step i: 子目标; key APIs used: ..." 的纯文本(C.4)。这些代码**不被运行时执行**,只作为上下文给 LLM 参考。prompt 还明确要求 "Never call other skills from the skills library"、"Avoid a functional style; there's no need to use return"(C.5–C.7),所以技能之间没有代码层面的调用或组合。没有 designer 角色,也没有 harness 这个概念:执行端是固定 ReAct 循环(§2 式 (1)),变化的只有 prompt 里的技能。

**b. 知识库结构:三层、跨层链接、多父、合并/拆分/过滤**
- 三层按"工具粒度"划分(§8 "from the perspective of tool granularity"):planning(任务级步骤)/ functional(子任务级工具组合)/ atomic(单工具)。
- **跨层没有显式边**。论文里 planning "specifying how functional skills should be composed",但存储上看不到 planning 指向 functional 的 id。层间关系只在检索时临时形成:pseudo-plan 的每一步作为 query 去召回 functional/atomic(§4)。仓库发布的 AppWorld 库(vanilla-iter3)里,`plan.json` 是 {训练任务 query → plan 文本} 的字典,72 条,也就是一个训练任务一条 plan,看不出合并;`func_atomic_skills.json` 68 条,字段只有 name/document/content/tools,没有 parent、member task 或证据字段。
- **多父/多组**:没有这个概念。functional skill 与 planning skill 之间是检索相似度上的多对多,不是存储的成员关系。没有任务簇、没有 membership 强度。
- **合并**:embedding 聚类(DBSCAN 0.9)→ LLM merge,合并后名称要泛化,"Notes and implementation should cover all plausible variants and edge cases";若两技能有包含关系则不合并,以保留 atomicity(C.5 Merge Guidelines 2)。
- **拆分**:合并结果过于复杂时 decompose(§3.3,C.5);抽取时也允许 "refactor it into more modular skills"(C.7)。
- **过滤**:General(可移植性/过度封装/引包)+ Tool-specific(对 schema 校验),都是 LLM 判 good/bad 或 correct/fail(C.1, C.3)。**没有用执行增益做过滤**,也没有"至少被 ≥2 个任务支持"之类的门槛;单条成功轨迹抽出的技能可以直接进库。

**c. 经验如何拆成技能?**
自上而下:成功轨迹 → 压成 plan(去掉探索/调试/失败步骤)→ 按 plan 的每一步抽一个 functional skill → 按轨迹里用到的每个工具抽一个 atomic skill(§3.2,C.4/C.6/C.7)。拆分的单位是"plan 步骤"和"工具",由 LLM 决定。**失败轨迹不参与**(只有 ExpeL 基线用失败轨迹,A.2);atomic skill 的 notes 里会写常见失败模式,但这些失败是从成功轨迹中出现过的报错里总结的。

**d. held-out 任务还是实例?跨环境/跨 agent 迁移?**
- **同 benchmark 内的 held-out 实例**。BFCL:multi-turn base 随机切 50 train / 150 test;AppWorld:90 个 train,测 Test-Normal;τ²:用官方各 domain 的 train/test(§5.1)。每个 benchmark 各建一个库(从论文表述和仓库按 benchmark 分目录推断;论文没明说"一库一 benchmark",但从未拿一个 benchmark 的库去测另一个)。AppWorld 的 test 与 train 有 "noticeable distribution gap"(A.1),算是最接近"新任务"的一处,但仍在同一 app 生态内。
- **跨环境迁移没做**。摘要和 README 说库 "can be reused across agents and environments",但 Limitations 自己承认技能绑定具体 tool schema,"direct reuse across substantially different domains or tool ecosystems less straightforward"。
- **跨 agent**:做了,这是主要卖点。GLM-4.6 抽的库给 Qwen3-32B、Kimi-K2、DeepSeek-V3.2、GPT-4.1(Table 1‡、Table 2 GLM-Extract)。

**e. 迁移/负迁移是否测量?**
没有任务 × 技能的迁移矩阵,也没有"哪些技能在哪些任务上有害"的分析。负迁移的证据散在各处,作者没有专门处理:
- Qwen3-32B 加 functional+atomic 反而掉,只开 planning 最好(§5.3 Fig. 3a),原因归为过度模仿;
- GPT-4.1 Self-Extract 两个 Pass@4 低于 No Memory(Table 2);
- 第 3 轮精炼回落(Table 3);
- Kimi-K2 BFCL 上 AWM‡ 64.67 < No Memory 65.17,τ² telecom 上 A-Mem 低于 No Memory(Table 1)。
它们的应对只是"不同模型选不同层组合",没有 per-task 或 per-skill 的取舍机制。

**f. 模型、预算、成本**
- 抽取/建库:GLM-4.6,每个训练任务 4 次 rollout(温度 0.9),最多 3 轮精炼,扩展阶段每个训练任务探索 1 次(温度 1.0)(§5.1, A.3)。每轮精炼都要在训练集上带库重新 rollout(式 (6)),所以建库总 rollout 大致是"训练任务数 × 4 × 轮数 + 探索",论文没给总数。
- 执行:Qwen3-32B、Kimi-K2-Instruct-0905、GLM-4.6、DeepSeek-V3.2、GPT-4.1;改写 pseudo-plan 与执行同一个模型(§5.1)。
- Embedding:Qwen3-Embedding-8B。
- **建库的 token、美元和墙钟成本都没报**。成本只出现在推理端的输入 token 与步数(Fig. 3e/f,文本只给定性结论)。

**g. Baselines 与主数字**
No Memory、A-Mem、AWM、ExpeL;AWM 与 ExpeL 各有 self(∗)和 GLM 抽取(‡)两版。所有方法都只按用户初始 query 检索,统一插入 system prompt(§5.1)。主数字见"结果"。要注意:
- Table 1 中 Qwen/Kimi 的 SkillX 只有 ‡ 版,**没有 SkillX 自抽版**;§5.2 说 "When the experience extraction model is aligned with the execution model, SkillX consistently outperforms all baseline methods",能支撑这句话的只有 GLM-4.6 那三行。
- 没有和 programmatic skill 类方法(ASI 2504.06821、Voyager)、Claude Skills、Trace2Skill、AutoSkill 等直接比,它们只在 related work 出现(§7)。
- 没有方差、CI 或显著性检验,只是 4 次运行的均值/pass@4。

**h. 泄漏控制**
这一项问题比较大:
- **式 (8) 及其下一句明说按测试集决定迭代轮数**:"max_k E_{q∼Q_test} ...","we stop the iteration when this test performance no longer improves"(§3.3)。没有 validation split。
- 主表 GLM-4.6 的 SkillX 行在 BFCL 上等于 Table 3 的 Vanilla-Iter2(79.50/86.00),在 AppWorld 上等于 Expand-Iter3(64.88/88.69)。也就是说**每个 benchmark 报的是消融表里不同配置**,而这些配置的选择依据只能是测试集,论文没说用了别的。
- 层组合也因模型而异(§5.3),同样看测试结果选。
- 检索阈值(0.45 / 0.08 / top-8 / MMR 0.75)怎么定的没说。
- BFCL 是随机切 50/150 实例,train 和 test 共用同一组函数集合和场景,技能里的 API 用法可以直接对上 test。
- 好的一面:抽取只用训练集 rollout 的成功信号;Tool-specific Filter 只用环境公开的 tool schema;扩展阶段合成的新任务来自环境探索,不看 test。
- 没有讨论 reward hacking 或技能对 evaluator 的过拟合。

**i. 代码/数据**
仓库 https://github.com/zjunlp/SkillX 已公开(见页首)。有完整 pipeline、prompt、AppWorld 技能库(vanilla-iter1/2/3,只有 vanilla 没有 expand 版)和三个 benchmark 的实验日志目录。论文 §8 承诺发布 "optimized skill library",目前只看到 AppWorld 的。BFCL 与 τ² 的库是否发布、日志里有什么,没逐一核对。

**j. 局限**
作者写的两条(Limitations):跨环境迁移受 tool schema 绑定限制;无函数调用的纯对话场景不是本文重点。§5.3 还提到训练数据少时文本优化会过拟合,轮数要选好。§6.2 说以工具 schema 为中心的经验学习是否适合 τ² 这种用户中心 benchmark "remains an open question"。我们补充的:没有建库成本;没有统计检验;测试集选轮数;层组合要按模型手选;层间无显式链接,"层级"主要体现在检索流程而不是存储结构;没有 per-skill 有效性归因。

## 与我们的区别

我们的方法:把完整 agent harness(冻结 LLM 外面的代码:prompt、记忆、控制流、解析)按任务逐个摄入,先过质量门(必须明显优于 base agent),由 Opus 写任务描述、能力、profile 和 harness 描述,再由 review 提炼共享功能为 `module` 与 `workflow` 节点;节点组成多父 DAG(soft hierarchy),每个节点有真代码、描述、父节点和成员任务,成员带可核对证据(该任务 harness 里的函数名或 ≥40 字符原文摘录),一个节点至少 2 个成员。新任务:探 3 题 → 描述 → 按 embedding 检索相似任务和节点 → 优先复用组合出首个 harness → 若干轮由 Opus 看 trace 判定的编辑。计划扩展:节点上挂 designer 侧经验条目(when/provide/use),证据来自版本历史(含失败尝试),membership 分 strong/medium/weak/negative。计划消融:flat 库 / 两层 / 单继承树 / soft hierarchy。设定:冻结 Qwen3.5-9B 玩文本游戏,训练 Wordle、Hangman、BabyAI、SciWorld、DC,测试 Mastermind、Minesweeper、ALFWorld、Twenty Questions、更难的 Wordle/Hangman、另一个 SciWorld 任务。

**重叠(直说)**
1. **"强模型从经验中蒸馏出多层、可复用、带代码的单元库,通过 embedding 检索给新任务用,弱模型受益"**,这句话两边都成立。审稿人很容易把我们说成 "SkillX for harnesses"。
2. 层次几乎能一一对上:我们的 `workflow`(一族任务怎么组合 module)≈ 他们的 planning skill("how functional skills should be composed");我们的 `module` ≈ functional skill(name + document + content + tools,content 是代码);他们的 atomic skill 对应我们 harness 里针对单个环境动作的解析/校验小件。
3. 构建流程相近:LLM 抽取 → 相似度聚类 → LLM 合并/拆分 → 质量过滤 → add/modify/keep,和我们 review 提炼节点的流程同一类。他们的 "merge 时如有包含关系就不合并以保 atomicity" 和我们 module/workflow 的分工也接近。
4. 使用端都是检索优先:他们先检索 planning skill 再按步骤召回下层,我们先检索相似任务再检索节点,"复用优先"的思路一样。
5. strong-to-weak 的叙事一样(GLM-4.6 → Qwen3-32B;Opus → Qwen3.5-9B)。
6. 对我们计划中的 designer 侧经验:**SkillX 没有这块,不构成重叠**。这一块的直接对手是 MetaSkill(2609.38143)的 when/provide/use。SkillX 最接近的是 atomic skill 的 "common failure modes" notes,但那是写给执行 agent 的,而且只从成功轨迹抽。

**SkillX 没做的**
1. **对象不同**:它共享的是放进执行模型 prompt 的文本(带代码片段),由 LLM 读、模仿;我们共享的是被运行时执行的 harness 代码,9B 模型看不到库,库的读者是 designer(Opus)。它的执行循环固定为 ReAct,不改控制流、记忆、解析。
2. **来源与质量门**:它只吃本系统 rollout 的成功轨迹,过滤是 LLM 判格式/可移植性/schema 合法;我们吃任意来源的完整 harness,并要求相对 base agent 有明显的执行增益。它从不检验单条技能是否真的带来增益。
3. **结构**:三层固定(按工具粒度),**层间无存储边、无多父、无成员关系、无证据、无 ≥2 任务支持门槛**;plan 在发布的库里是一题一条,没有合并。技能之间被 prompt 明令禁止互相调用。我们是多父 DAG,节点带成员与可核对证据,module/workflow 有真实的调用/组合关系。
4. **迁移范围**:只测同 benchmark 的 held-out 实例,一库一 benchmark;跨环境被列为局限。我们测的是**训练里没出现过的任务族**(Mastermind、Minesweeper、ALFWorld、Twenty Questions),这是最清楚的差异。
5. **负迁移**:有现象(Qwen 只开 planning 最好、GPT-4.1 自抽 Pass@4 下降、第 3 轮回落),没有机制。我们计划的 negative membership 正好对应这一缺口。
6. **结构消融**:它的消融只是"开哪几层",内容随层一起变,所以"hierarchical representation matters" 和"内容多少"混在一起,没有"同样内容、flat vs 分层"的对照。我们计划的 flat / 两层 / 单继承树 / soft hierarchy 在同一批节点上比,能把结构的作用单独拿出来。
7. 没有成本账,没有统计检验,也没有对话以外的游戏/部分可观测任务。

**审稿人可能的攻击与应对**
- "分层技能库 + 检索复用已经被 SkillX(还有 AWM、ASI、AutoSkill、Trace2Skill)做过,你们只是把 skill 换成 harness 代码。"
  应对:差异放在三处讲清楚。(i) 库的消费者是 designer,产物是执行的 harness,不是 actor prompt;(ii) 结构上是带证据的多父成员关系,并用同内容的 flat/tree/soft 消融证明结构本身有用;(iii) 测的是未见任务族,SkillX 自己承认跨环境做不到。**最好把 SkillX 当 baseline 跑**(代码公开):用训练游戏上的 base-agent 或 harness 轨迹建 SkillX 库,注入 Qwen3.5-9B 的 system prompt,在测试游戏上比。可以再加一个变体:把 SkillX 库交给 Opus 当 designer 的参考,隔离"表示"与"消费者"两个因素。
- "你们的 module / workflow 就是 functional / planning skill 换了名字。"
  应对:承认对应关系,在 related work 里主动写出来;强调我们的节点有成员与证据,并且 workflow 真的调用 module(SkillX 禁止技能互调)。
- "为什么不直接把技能给 LLM,更便宜?"
  应对:引用 SkillX 自己的结果:Qwen3-32B 加 functional/atomic 技能会因 "over-imitate retrieved skills" 而掉分(§5.3)。我们用的是更小的 9B 模型,把经验放进它执行不到的代码里,正好避开这个问题。这是 SkillX 给我们的论据。
- "你们的分层是事后贴的,不就是 SkillX 的三层?"
  应对:三层是按工具粒度预设的,我们的层由 review 从成员证据里长出来,需要展示实际出现的多父节点及其被新任务复用的频率,并做 tree vs soft 消融。
- "迭代编辑/选择也可能用了测试集。"
  应对:SkillX 用测试集停迭代、按 benchmark 选配置(§3.3 式 (8),Table 1 vs Table 3),我们要在协议里写死测试任务不参与任何选择,和它形成对比,但正文里点到即可。

**结论**:SkillX 和我们在"强模型蒸馏多层可复用单元 + 检索复用 + strong-to-weak"这个层面重叠很高,module/workflow 与 functional/planning 的对应也很直接,必须引用并当 baseline 跑。它没有碰的是:库被 designer 消费、以可执行 harness 为单元;带证据的多父成员关系和负成员;跨任务族迁移;同内容下的结构消融。designer 侧经验那条线的对手是 MetaSkill,不是 SkillX。另外它关于弱模型过度模仿 prompt 内技能的发现,可以直接用来说明我们为什么把经验放进 harness 代码而不是 prompt。
