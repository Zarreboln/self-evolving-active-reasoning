## 任务

在 domain-specific 工作流上自动化 **harness engineering**,即自动设计让 foundation model 能干活的 prompts、tools、orchestration logic 和 evaluation criteria。Abstract 举的例子有:企业 web 应用的多步点击和表单填写、search→extraction→synthesis 研究流水线、陌生仓库里的 code review、客户升级工单处理。

- 任务形式化(§2.2):t = (I, S),I 是 instructions,S = {s1..sm} 是一份可验证的 success criteria checklist。
- Agent = Model + Harness(§2.1,沿用 Trivedy 2026)。harness 指模型参数以外的所有代码、配置和执行逻辑。

## 问题

§1 的论点:手工设计的 harness 效果好(Lopopolo 2026 / Rajasekaran 2026 两篇工程博客),但每换一个领域都要专家重新设计和调参。LLM-AutoDiff 这类 prompt 优化方法"can tune individual components",却管不到整个 harness,也就是 tools、orchestration、infrastructure 以及它们之间的交互。更进一步,自动做 harness 进化的那套流程本身也是人设计、固定不变的(§3:"In the current system, Λ is designed by human engineers and remains fixed")。

## 方法

**两层循环。**

**内层:Harness Evolution Loop(§2,Algorithm 1)**,针对单个任务:
- Worker Agent W_H:跑任务,输出 trace τ(环境观测、动作日志、每步耗时)(§2.3)。
- Evaluator Agent V:对抗式审查(§2.4),做 4 件事:(1) state verification,用 ground-truth 环境状态核对 worker 声称看到的东西,抓幻觉;(2) 对每条 s_i 判 pass/fail;(3) performance auditing,把耗时拆成 LLM time 和 tool time;(4) scoring,用两级指标,先比 pass/fail,再用执行时间做 tiebreaker。
- Evolution Agent E:读完整 history,即 (H, report, score, verdict) 序列,把失败归类(错误 tool usage、reasoning loops、环境状态误读、延迟过高),再改 harness(tool 实现、system prompt、orchestration、observation 结构、model 配置),但不改模型参数(§2.5)。
- Alg.1:迭代 K 步。每步开始前环境 reset 到干净状态。**总是从 H(best) 出发去 evolve**(第 14 行),score 比历史最好高就记 IMPROVED,否则记 REGRESSED。最后返回 H(best)。

**外层:Meta-Evolution Loop(§3,Algorithm 2)**:
- 把整个内层流程打包成 evolution blueprint **Λ = (W_H, H(0), V, E)**(式 1),认为 Λ 本身也是一个 harness(§3.1)。
- Meta-Evolution Agent E_meta 可以改的东西(§3.1 列表):evaluator prompt、evolution agent prompt、worker observation structure、evaluator 和 evolution agent 之间的 observations、scoring function 设计、loop hyperparameters(迭代数、并行度、revert 阈值、停止条件)。式 1 把 H(0)(初始 worker harness)也放进 Λ,但 §3.1 的可修改列表里没有明确写 H(0)。
- Alg.2:每轮在 T_train 的每个任务上跑一次 Alg.1。meta_score = Aggregate = **各任务 best score 的均值**(第 9 行)。仍然从 Λ(best) 出发 evolve。第 3 行 `for j = 0,1,2,...` 没有写外层停止条件。
- 目标(式 2):Λ(best) = argmax_Λ E_{ti~T_train}[best_score(HarnessEvolutionLoop(ti, Λ, K))]。论文明说 "judged solely by the final best score ... not by intermediate progress"。注意 §3.2 的文字说外层目标是 "improve the speed of adaptation",和式 2 只看最终分数不一致,论文没有处理这处矛盾。
- Table 1 给出和 meta-learning 的对应:θ↔H,adaptation procedure↔Λ,inner gradient↔Alg.1,meta-gradient↔E_meta.evolve,meta-test↔T_test。
- 评测协议(§3.3,只是提出,没有执行):在 T_test 上看 convergence speed(达到阈值所需迭代数)、final performance(固定迭代数后的 pass rate)、robustness(不同 meta-test 任务之间收敛速度的方差)。

## 对照问题 a–j

**a. 跨任务共享/元学习的是什么?**
是 evolution blueprint Λ = (W_H, H(0), V, E)(式 1,§3.1),也就是改进 harness 的那套流程:evaluator prompt、evolution agent prompt、observation 结构、scoring function、loop 超参;按式 1,初始 harness H(0) 也算在内。**不是**把 worker harness 本身的代码或组件库作为跨任务共享对象。每个任务的 H(best) 留在各自的内层,不回流,Alg.2 第 6–7 行只把 score 和 history 交给外层。不过 E_meta 能读到各任务的 history(第 15 行,meta_history 含 task_results),所以理论上可以把共性写进 H(0) 或 E 的 prompt。但论文没有把这件事作为机制写出来。

**b. 共享结构?**
严格的两层:一个全局 Λ,加上 per-task 的内层适配(Alg.2;式 2 对 T_train 取均值)。没有分级、层次、聚类或 soft membership。**没有建模任务相似度或任务簇**,只用 Aggregate=mean 把所有任务一视同仁。

**c. harness 是否拆成组件/槽位?**
§2.1 列了 6 类组件:system/task prompts;tools/skills 及其描述;bundled infrastructure;orchestration logic;hooks/middleware;model configurations。§3.1 也列了 Λ 的 6 类可改部分。但这些只是**描述性分类**,不是算法里用到的固定槽位或接口。E 直接改"every piece of code and configuration"(§2.5)。组件既不是学出来的,也不是被强制执行的结构。

**d. 评测是 held-out tasks 还是 held-out instances?benchmark?交互式?**
协议上写的是 held-out **tasks**(T_test,§3.2–3.3:"given a new, unseen task"),并且 T_train 是 "potentially different domains"。但没有跑:任务数、benchmark、交互性全都**论文未说明**。动机里的例子(web 表单、研究流水线、客服)是 agentic 多步任务;WebArena 只在介绍 OpAgent 时提到,不是他们的评测。他们的任务定义是 I + S checklist,**没有涉及部分可观测、主动提问或信息收集**这一类任务。

**e. transfer matrix / 负迁移 / 迁移预测因素?**
没有。论文未说明。

**f. 内层预算、proposer 模型、冻结 worker、算力成本?**
内层预算只有符号 K,没有给值。没有给出 E、V、E_meta 用的模型。worker 只说可以是 AdaL、Claude Code、Codex、OpAgent(§2.3)。而且 harness 包含 "model configurations",E 可以换 worker 用的模型(§2.1、§2.5),所以 **worker 模型不一定冻结**,只是模型参数不训练。算力和成本论文未说明。

**g. Baselines 与主结果?**
没有。论文未说明。§3.3 只说预期比 "a manually designed harness evolution loop" 迭代少、算力省。

**h. 泄漏、过拟合、reward hacking 控制?**
有的只是**设计层面**的部分措施:V 与 E 分开,且 V 是"adversarial reviewer";V 用 ground-truth 环境状态核对 worker 的声明,防幻觉(§2.4);每次迭代都 reset 环境(Alg.1 第 5 行);meta-train 和 meta-test 分开(§3.2)。缺的部分:**内层没有 train/selection/test split**。Alg.1 在同一个任务 t 上反复执行、打分、选 best,也就是在评测实例上直接做选择。E 能否看到 S 或 evaluator 的内部判据,论文未说明。外层的 Λ(best) 用 T_train 上的分数选,没有独立的 meta-validation 集。

**i. 代码/数据发布?**
论文里没有代码链接,§4 说的是未来会"release a product"。网络搜索(alphaxiv、emergentmind、themoonlight、ericfode agent-harness-wiki 等)**没有找到官方 GitHub repo**。PyPI 上有一个名字相近的 polyharness,但不是这篇论文的发布物。

**j. 自述局限与 future work?**
论文没有局限性小节。§3 承认 "In the current system, Λ is designed by human engineers and remains fixed",并把 Meta-Evolution 称作 "a natural generalization"。读起来,外层很可能还没实现。§4 的 future work:在"complex customized customer workflows"和"domain-specific enterprise processes"上给出实证;发布一个基于 Λ(best) 的产品。

## 与我们的区别

我们的计划:冻结的 Qwen3.5-9B;约 17 个文本 benchmark、约 100 个子任务,都是部分可观测下的主动推理;内层 = Meta-Harness 式的 per-task harness 代码进化,proposer 用 Opus;外层 = 在代码 edit 上做层次化 Reptile,把反复出现的 edit 提升为共享组件,任务对组件是**连续(模糊)隶属**,也就是在任务子集之间部分共享;在 held-out tasks 上评测并报 adaptation curves;科学问题是迁移结构是否沿着信息收集问题的维度(hypothesis space、observation channel、cost、stopping)组织,而不是沿着 benchmark 身份组织。

**它已经占掉的(审稿人可以拿来引用的部分):**
1. "harness design = bi-level meta-learning"这个**框架表述本身**:inner loop 把 harness 适配到单个任务,outer loop 优化适配流程以泛化到新任务,外加 Table 1 和 meta-learning 的对应。我们的 intro 如果写成"we cast harness evolution as meta-learning",会被直接指出这里已经有人写过。
2. 在 held-out tasks 上看收敛速度和最终性能的评测**协议**(§3.3)。这和我们的 adaptation curves 在概念上重合。
3. "进化 harness 的流程本身也是 harness,可以被元优化"的说法(§3.1)。

**它没有做的(我们的空间):**
1. **没有任何实证**。没有 benchmark、数字、baseline 和代码。我们会是第一个真正量化 bi-level harness meta-learning 的工作,至少相对这篇是这样。
2. **共享对象不同**。它元学习的是**流程**Λ(evaluator/evolver 的 prompt、scoring、超参),不是 worker harness 的**代码组件**。我们共享的是从 per-task edit 里蒸馏出来的 worker 侧 harness 组件,性质上更接近 Reptile 在参数空间做插值,而它更像在学 optimizer。两者可以正交组合。
3. **共享结构不同**。它是一个全局 Λ 加上 mean 聚合,没有任务相似度、簇、层次或 soft membership。我们的连续隶属和部分共享在这篇里完全没有。
4. **没有组件化的算法**。§2.1 的组件分类只是描述性的;它没有"把反复出现的 edit 提升为共享组件"这样的机制。
5. **任务类型不同**。它没有涉及部分可观测、主动提问或信息收集;它的任务是带 checklist S 的工作流完成。
6. **没有 transfer matrix、负迁移分析,也没有"什么决定迁移"的科学问题**。我们的 IG 维度假设(hypothesis space / observation channel / cost / stopping vs benchmark identity)在这里完全没有。
7. **worker 不冻结**。它允许 E 换模型(model configurations),而我们固定小模型,这一点更干净。
8. **它的内层直接在评测任务上选 best**,没有 selection split。我们在泄漏控制上可以明显更严。

**审稿人可能的攻击方式及应对:**
- 攻击:"Bi-level harness evolution with an outer loop for cross-task generalization was already proposed by Seong et al. (2604.21003); the contribution reduces to an instantiation."
  应对:承认框架层面的先例,定位成**第一个实证化的版本**,并强调两点实质区别。其一,共享的是 worker 侧代码组件,用 Reptile 式聚合,而不是流程 prompt;其二,任务之间是**结构化的部分共享**(连续隶属),而不是一个全局 Λ。
- 攻击:"Reptile over code edits is just their E_meta reading meta_history."
  应对:它的 E_meta 是用 LLM 自由改 Λ,没有显式的 edit 聚合、提升规则或隶属模型。我们需要把 promotion 的判据和隶属的估计写成可复现的算法,并且用消融证明:全局共享(相当于它的结构)< 我们的软分组。**这个消融是让区别站住的关键实验,必须做。**
- 攻击:"Held-out task adaptation curves follow their §3.3 protocol."
  应对:引用它,并说明我们真正执行了这个协议,而且额外报告了 transfer matrix 和负迁移。
