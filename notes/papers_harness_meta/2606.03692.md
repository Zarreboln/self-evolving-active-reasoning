## 任务

文本交互式 agent:给自然语言任务指令 x,agent 每步看观测 o_t、出动作 a_t,episode 结束拿 reward r∈[0,1] 或成功信号(§2.1)。Agent 是 ReAct 式 Thought/Action 循环,检索到的 skill 文本插进 system prompt 的 `{{skill_reference}}` 槽(附录 A.12)。评测在 ALFWorld、ScienceWorld、WebShop,外加附录的 GAIA-Lite(§3.1,§5)。

## 问题

已有 skill 管理框架(SkillNet、SkillX、Skill-Pro 等)有两个不足(§1):"(i) existing skills are typically reused as stored units, leaving their internal transferable experience underexploited; and (ii) new skills are often retrieved, refined, or appended rather than composed from prior skill experience." 扁平 skill 库遇到没有直接匹配的新任务时,agent 只能从零探索(Fig. 1a)。作者要回答的是:"how can skills evolve from isolated, task-specific solutions into reusable, compositional knowledge?"

## 方法

- **Skill 表示**(§2.1):s=(n, d, c),"a structured natural language program"。n=名字,d=短描述,c=适用条件、执行流程、输入输出。落地为 `SKILL.md` 文件,固定小节为 Purpose / When to Use / Inputs / Workflow / Verification / Constraints / Output(A.12 Builder 输出格式)。另加依赖字段 δ,里面放复用引用 ρ=(名字, 唯一 id, 何时复用 w, 提供什么能力 o),文本格式为 `[reuse skill: <name> | when: <trigger> | provides: <capability>]`(式 (4),A.12)。**全是自然语言,不是代码。**
- **Pyramid**:P={L0,…,LK},从下往上越来越抽象、越来越组合(§2.1)。
- **Relation Analyzer**(§2.2.1):先做 coarse grouping,只看名字+描述(式 (1);A.5 说还用 Qwen3-Embedding-4B 相似度做候选筛选)。再对每个粗组并行做 fine-grained 分析,可调工具读完整 skill 内容,最多 t 轮(A.5:5 轮),输出若干 (g_k, τ_k, e_k):细粒度子集、关系类型、自然语言理由(式 (2))。一个粗组可以产出多个子集。Prompt 分 SCREEN / DECIDE 两阶段(A.12)。
- **Relation Builder**(§2.2.2),两种模式:
  - Downward Atomic Extraction:从 g_k 抽出公共功能部件作为 atomic skill a_k(式 (3)),再把每个源 skill 改写成通过复用引用调用 a_k(式 (4))。层号 ℓ(a_k)=min ℓ(s)−1(式 (5))。prompt 里细分三种关系:SHARED_PART(多 skill 共享具体子能力)、SUBSET(一个是另一个的严格子技能,只改写较宽的那个)、MERGE(近乎等价则合并为一个 canonical skill)(A.12)。规则要求 "the new skill must be narrower than every source skill"。
  - Upward Abstract Induction:从 g_k 归纳 abstract skill u_k,"describe how lower-level skills should be organized to solve a class of related tasks"(式 (6));层号 ℓ(u_k)=max ℓ(s)+1(式 (7))。prompt 要求 "Do not merge or replace the children"、"must be higher-level guidance, not a concrete action script"。
  - Analyzer–Builder 外循环最多 T 轮(A.5:3 轮),直到不再产生新 skill(Algorithm 1)。
- **Skill Creator**(§2.3):对新任务 x 检索 R(x)⊆S("jointly considering task semantics, applicable conditions, and the constraints encoded in the pyramid"),两阶段生成:(i) framework construction,优先用高层 abstract skill 定结构;(ii) detail instantiation,优先用 atomic skill 填操作、检查、输出。有现成 skill 完全覆盖就直接复用,否则 ŝ=C_create(x, R(x), P)(式 (8))。阶段相关的检索权重实现这种优先级(A.12)。
- **Self-Evolution**(§2.4,Algorithm 1):对任务流里的每个 x,生成 ŝ → 执行 → **成功则用成功轨迹 refine ŝ 并保留,失败则丢弃**。保留的 ŝ 作为 query,只检索相关的已有 skill 做局部关系构建,得到 ΔP_t 增量插入(式 (9))。插入后做结构校验:错边、层级不一致、非法跨层、自环;复用边只能从高层指向低层,所以没有多节点环(A.7)。

## 对照问题 a–j

**a. 共享的是什么?文本还是代码?给谁用?**
共享的是**自然语言 skill(`SKILL.md`)**,"a structured natural language program"(§2.1),不是代码。Skill 给**执行 agent** 用:检索到的 skill 插进 ReAct system prompt 的 `{{skill_reference}}` 槽(A.12)。agent 本身的脚手架(ReAct 循环、Thought/Action 格式、解析)对所有方法固定,不进化也不共享。skill 间的"调用"是文本里的 `[reuse skill: … | when: … | provides: …]` 引用,没有可执行的调用语义。

**b. 结构:层级 skill topology**
- 层:L0…LK,层号由构建规则决定,atomic 放在 min−1,abstract 放在 max+1(式 (5)(7))。层数不固定,论文没报最终有几层、每层多少节点。
- 合并(consolidation)两条路:Downward Atomic Extraction(SHARED_PART / SUBSET / MERGE)和 Upward Abstract Induction(A.12)。只有 MERGE 真正删除重复,其余都是加节点、加引用。
- **多父 / 重叠成员**:一个 atomic skill 被 g_k 里所有源 skill 引用,所以天然是多"父";一个 skill 的 δ 字段可以放多条引用,也可以在多轮 Analyzer–Builder 中进入不同 g_k。结构是**分层 DAG**,边只能从高层指向低层(A.7)。论文没有讨论 coarse group 是否互斥(式 (1) 只说 "G0m ⊆ S"),也没把"多父/软成员"作为设计点或做消融。
- 组合:新任务时 Skill Creator 先用 abstract skill 搭框架,再用 atomic skill 填细节(§2.3);abstract skill 的 δ 记录它组合了哪些低层 skill(§2.2.2)。
- 节点成立条件:SHARED_PART 要求 "Multiple skills share a concrete reusable sub-capability",abstract 要求 "peer skills share a higher-level solving pattern"(A.12)。**没有可检查的证据要求**(如函数名、原文片段);正确性只靠 prompt 里的 "Be conservative and evidence-grounded" 和事后人工抽查(Table 8,abstract 错 20%)。

**c. 分解**
有两向分解:向下把公共子流程抽成 atomic skill 并改写源 skill;向上归纳 task schema。分解的粒度、类别(atomic/abstract 两轴)是作者手定的;作者在 Limitations 承认 "the pyramid models only two reuse axes and does not capture richer temporal or causal relations"。被分解的对象是**一条条 skill 文本**,不是 agent 的完整程序或 harness。

**d. held-out 任务还是实例?迁移到新场景?**
**同 benchmark 内的 held-out 实例**。三个 benchmark 各建各的库("the three benchmarks use separate skill libraries",A.5),初始库只来自对应 benchmark 的 train split。"Unseen" 的定义(A.1):ALFWorld = `eval_out_of_distribution`(134 题,同 6 类任务、未见房间);ScienceWorld = `test_indices.json`(211 个 variation,与 seen 同属 24 个 task type)。WebShop 只有一个 200 题集合。所以 "unseen tasks" 实为**同任务类型的新实例**,没有跨 benchmark、也没有留出整个任务类型。最接近"新场景"的是 GAIA-Lite(用网上挖的 skill,不是从前三个 benchmark 迁移)和 RoboEgo-7B 换 backbone(A.4)。

**e. 迁移/负迁移的测量**
没有任务×skill 或 benchmark×benchmark 迁移矩阵,也没有跨 benchmark 迁移实验。负效应只零散出现:scratch-generation 低于 flat(Table 2);3B 构建模型、高度模糊 skill 时 ALFWorld 低于 flat(Table 11/12);WebShop 失败分析指出 abstract induction 会 "remove rare but essential lexical attributes",造成过度泛化(A.10)。Table 3 的 atomic-heavy / abstract-heavy 分组是最接近"什么预测收益"的分析,但只针对两种 skill 类型,不针对任务间迁移。

**f. 模型、预算、成本**
- 执行 agent(被测):DeepSeek-V3.2、GPT-4.1、Gemini 2.5 Pro、Qwen3-235B,temperature 0(§3.1);附录另有 GPT-5.5 Codex(Table 6)和 7B RoboEgo(Table 7)。
- 构建模型:"Qwen3.5-35B-A3B as the backbone model for all construction agents",embedding 用 Qwen3-Embedding-4B(A.5)。Skill Creator 在评测时是否也用 Qwen3.5-35B-A3B,论文没有明说("construction agents" 是否包括 Creator 不清楚;代码里分 TESTED / FRAMEWORK 两套模型)。
- 外循环 ≤3 轮,fine-grained analyzer ≤5 轮(A.5)。步数上限论文没写;repo 构建脚本默认 `MAX_STEPS=30`、`TOP_K=5`、`HOPS=1`、`MAX_VISIBLE_SKILLS=5`、ALFWorld 构建用 60 局 train。
- 成本(A.11):构建一次 8.4K 次调用(21.6M 输入 / 3.1M 输出 token);主评测 315K 次(0.92B / 46.8M);消融分析 24K 次(71.5M / 5.4M)。主评测 17,580 个 episode(879 实例 × 5 方法 × 4 backbone)。没报美元和墙钟时间。不训练任何参数。

**g. Baselines 与主数字**
- 正文 baseline:ReAct、Reflexion、ExpeL、ReAct+Skills(同初始库、扁平检索插 prompt)(§3.1,A.2)。附录加 SkillNet、SkillX(只在 ALFWorld unseen + DeepSeek 一格,Table 5)和 GPT-5.5 Codex(Table 6)。
- 主数字见"结果"。**关键:38.0% / 27.7% 的基线是无 skill 的 ReAct**,不是同库的 ReAct+Skills;对 ReAct+Skills 是 73.7 vs 65.8(+7.9),14.6 vs 17.7 步;对最强 skill 框架 SkillNet 只有 +1.2(单格)。
- ALFWorld(DeepSeek)seen/unseen 81.4/84.8;ScienceWorld(DeepSeek)seen/unseen 76.3/79.1;WebShop 32.0。四个 backbone 里 ALFWorld unseen 最高 91.0(Qwen3-235B),ScienceWorld unseen 最高 88.6(GPT-4.1)。
- **没有和 harness/agent-design 搜索类方法比**(Meta-Harness、ADAS、AFlow 等),related work 也没提。

**h. 泄漏控制**
- 初始库只来自 train split,"No evaluation task or trajectory is used during initial pyramid construction"(A.5)。
- 但**评测本身就是 self-evolution 的任务流**:每道评测题生成 ŝ、执行,**用该题的成功信号**决定保留与否,保留的 skill 给后续评测题用("Admitted skills are available only to subsequent tasks",A.5)。这是用测试环境 reward 的 transductive 设定,分数是第一次尝试的结果(Algorithm 1 第 14–21 行),但后面的题受益于前面测试题的成功轨迹。论文没把这一点当泄漏讨论;唯一的间接对照是冻结 pyramid 的 w/o self-evolution(ALFWorld seen 76.4,仍高于 flat 75.7,Table 2),而且只有 DeepSeek 两格。
- 用 oracle 轨迹做 Table 3 的任务分组(只用于分析)。
- 没有单独 validation split;没有 reward hacking 讨论。成功门控 "does not guarantee semantic correctness",也没有回滚(Limitations)。
- 初始库来源细节不透明:论文只说"constructed from the training splits";repo 构建脚本显示是从 `flow/skill-collections/initial_hand/<env>` 的**手写 seed** 起步,再在 train 局上生成,而这个 seed 目录不在仓库里。初始库规模 ALFWorld 65、ScienceWorld 913、WebShop 71(A.5)。

## 与我们的区别

我们的方法:把完整 agent harness(冻结 LLM 外面的代码:prompt、memory、控制流、解析)分解成新任务可复用的 soft hierarchy。harness 来源不限(Meta-Harness 进化或人写),须过质量门(明显赢 base agent),逐任务摄入:Opus 根据 3 条 base-agent 轨迹写任务描述 + 能力 + profile,再写 harness 描述,再 "review" 把共享功能提炼成节点:`module`(小的可复用部件)和 `workflow`(一族任务怎样组装 module);节点构成多父 DAG,每个节点有真代码、描述、父节点、成员任务及可检查证据(该任务 harness 里的函数名或 ≥40 字符原文片段),≥2 个成员才成立。新任务:探 3 题、写描述、按 embedding 检索相似任务与节点、先复用地组出第一版 harness,再由 Opus 看轨迹做少量编辑。计划扩展:挂在节点上的设计者侧经验条目(when/provide/use),证据来自含失败尝试的版本历史。计划消融:flat / 两层 / 单继承树 / soft hierarchy。设定:冻结 Qwen3.5-9B 玩文本游戏(Wordle、Hangman、BabyAI、SciWorld、DC;测试 Mastermind、Minesweeper、ALFWorld、Twenty Questions、更难的 Wordle/Hangman、另一个 SciWorld 任务)。

**重叠(说直白点,这篇和我们撞得很近)**
1. **结构几乎一一对应**:他们的 atomic skill ≈ 我们的 `module`("minimal reusable capability that appears across multiple skills");abstract skill ≈ 我们的 `workflow`("describe how lower-level skills should be organized to solve a class of related tasks")。都是 LLM 从已有产物里自下而上提炼共享部分,都是 ≥2 个来源才建节点,都是多"父"引用的 DAG。
2. **流程同构**:逐个摄入新产物 → 检索相关已有节点 → 局部建关系(他们的 self-evolution ≈ 我们的逐任务 ingest + review);新任务 → embedding 检索 → "先复用"地组合(他们 abstract 搭框架、atomic 填细节,我们 workflow + module)。他们也有质量门(只收成功的 ŝ),我们是"明显赢 base agent"。
3. **同样的核心消融**:flat vs 层级(ReAct+Skills vs pyramid,Table 1/2;Flat vs Pyramid web skills,Table 4),还有 "scratch-generated" 对照,正对应我们的"不复用、从零写"对照。
4. **benchmark 重叠**:ALFWorld 和 ScienceWorld 都是他们的主表,我们的测试集里有 ALFWorld,训练和测试里都有 SciWorld。审稿人一看就会问"为什么不和 SkillPyramid 比"。他们的代码 MIT 公开,没理由不跑。
5. Analyzer 用名字+描述粗分组、再读全文细分析,与我们"先写任务/harness 描述,再 review"的两段式也相似。

**他们没做的(我们的空间)**
1. **共享单位是 NL skill 文本,不是 harness 代码**。他们的 agent 脚手架(ReAct 循环、解析、记忆、控制流)固定不动,skill 只是 prompt 里的一段说明;"复用引用"是文本标注,不能执行。我们共享的是可运行的代码节点,能改控制流、状态跟踪、解析和记忆,这些 NL skill 改不了。
2. **没有跨 benchmark 的任何共享或迁移**:三个 benchmark 各一个库,"unseen" 只是同任务类型的新实例(ALFWorld OOD 房间、ScienceWorld 同 24 类的 test variation)。我们是跨多个游戏共用一个层级,测试是**留出的任务族**(Mastermind、Minesweeper、Twenty Questions,ALFWorld 本身对我们也是留出任务)。
3. **没有可检查的成员证据**:节点对不对只靠 prompt 自律和事后小样本人工审计,abstract 错误率 20%。我们要求每个成员任务给出函数名或 ≥40 字符原文片段,可机器核对。
4. **没有层级形态的比较**:只有 flat vs pyramid,层号用固定规则(min−1 / max+1),没有单继承树、两层、soft DAG 之间的对照。我们的四档消融正好补这块。
5. **没有 per-task 迭代**:新任务生成一次 ŝ、跑一次,成功就收,失败就丢;没有看轨迹改几轮。我们有 Opus 依据轨迹的编辑步。
6. **失败信息全扔掉**:失败的 ŝ 直接 discard,没有设计者侧经验或失败历史。我们计划的 when/provide/use 经验条目带失败尝试证据,这部分他们完全没有。
7. **都是大 API 模型**:执行 agent 是 DeepSeek-V3.2 / GPT-4.1 / Gemini 2.5 Pro / Qwen3-235B;唯一的小模型实验(7B RoboEgo)只涨 2.3 分(27.6→29.9)。我们是冻结 9B。
8. 没和 harness 搜索方法(Meta-Harness、ADAS 等)比,也不引用。

**审稿人可能的攻击与应对**
- **"module/workflow 就是 SkillPyramid 的 atomic/abstract,换成代码而已。"** 应对:(i) 单位不同:我们分解的是完整 harness 程序,节点可执行、可单测,能改变解析/控制流/记忆这些 prompt 管不到的部分;(ii) 正面实验:在同一冻结 Qwen3.5-9B、同一任务上跑 SkillPyramid 官方代码(用我们的 harness 描述或轨迹造初始 skill 库),表明 NL skill 层级在小模型上收益有限。他们自己的 RoboEgo-7B 只 +2.3 可以引用作 motivation(措辞要准:那是 ALFWorld unseen、ReAct+Skills→Pyramid)。
- **"层级优于扁平已被 SkillPyramid 证明。"** 应对:他们只比了 flat vs 一种固定规则的金字塔;我们的贡献在比较层级形态(两层 / 单继承树 / 多父 soft DAG),并且在跨任务族留出上测。这要求我们的消融真的显示 soft DAG 有独立收益,否则这一点会站不住。
- **"ALFWorld/SciWorld 上你们的数比 SkillPyramid 低很多(他们 ALFWorld unseen 84.8–91.0)。"** 应对:设定不同,他们用 235B 级 API 模型 + ALFWorld 自己 train split 建的库;我们是 9B、ALFWorld 完全留出(没有任何 ALFWorld 来源的 harness)。表里要把"库是否见过该 benchmark"和 backbone 列清楚;最好补一个在同 backbone 上的 SkillPyramid 数。
- **"你们的 SciWorld 测试任务和训练用的 SciWorld 是同一个 benchmark,不算留出。"** 应对:我们留出的是另一个 SciWorld task type,比他们的"同 24 类、换 variation"严格;但要在文中老实区分"同 benchmark 新任务类型"与"新 benchmark"两档。
- **"他们也有质量门和自进化。"** 应对:他们的门是测试题自己的成功信号(transductive,用测试 reward 决定收录),我们的门在摄入阶段用 base agent 对照,测试题不回流进库。这点应在我们的协议里写明,作为与他们的区别。
- **"他们的 Analyzer/Builder 有 SHARED_PART/SUBSET/MERGE 的细分,你们的 review 更粗。"** 应对:我们靠可检查证据而非关系类型来约束;可以引用他们 Table 8 的 20% abstract 错误率,说明没有证据约束时提炼不可靠。

**结论**:SkillPyramid 在"动机 + 结构形状 + 流程"三层都和我们高度重叠:自下而上提炼 atomic/abstract(≈module/workflow)、多引用 DAG、检索后先复用再组合、逐个摄入、flat vs 层级消融,而且同样用 ALFWorld 和 ScienceWorld。真正的区别在:共享单位是完整 harness 代码而非 prompt 里的 NL skill;一个库跨多个 benchmark,测试留出任务族,而不是每个 benchmark 各一库、只测新实例;节点成员要有可检查证据;比较多种层级形态;冻结小模型。论文必须引用它,related work 里要正面写区别,并且应当把它(官方代码,MIT)作为同 backbone 的 baseline 在 ALFWorld 和 SciWorld 上跑一遍,否则 "flat→hierarchy" 这一点会被认为已被它占掉。
