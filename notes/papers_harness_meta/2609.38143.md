## 任务

Test-time AI4AI:Builder 和 Target 两个模型权重都冻结,Builder 给 Target 写 task-specific harness(instructions + resources + executable mechanisms),Target 在 harness 里解题。目标是式 (1):在 Target 执行预算 $C_x$ 内最大化测试集期望分数 $J(H)$;预算只算 Target 执行,不算 Builder 建 harness 的计算(§3 Problem Formulation)。

## 问题

Builder 每道题从零建 harness,经验不能复用。论文要问的是:Builder 怎样把自己所建 harness 的执行结果变成可复用的知识,用来支持以后的任务(§1)。作者把 Target 用的 task skill("怎么做任务")和 Builder 需要的 support principle("怎么设计支持")区分开,后者叫 meta-skill(§1)。

## 方法

- **Meta-skill 的定义**(§3.1):三元组 s = (when, provide, use)。when=需要支持的可观察条件;provide=环境应提供的能力/资源;use=Target 怎么用它、哪些判断仍归 Target。三个字段合计 ≤192 tokens(附录 B.1)。是自然语言文本,不是代码。
- **学习循环**(§3.1 式 (2)):bank 从 $S_0=\emptyset$ 开始。对每个 development task,Builder 拿 $H_0$、公开组件接口和**完整当前 bank** 构建 harness → Target 执行 → Builder 看自己的程序 + 公开执行反馈 $F(e)$(提交物、input–observation 对、公开报错、最终产物、harness 递送的支持)→ 做一个决定:keep / revise / add。每个 batch(§4.1 写的是"per task")最多一次 add 或 revise,并且必须引用本 batch 的证据;旧版本存档(B.1)。development set 跑两遍(two passes)。
- **测试**(§3.2 式 (3)):bank 冻结;每个 test task 由 Builder 依据 full bank 或 BM25 top-2(k1=1.5, b=0.75,只取正分,query=初始公开 prompt;附录 C)在新环境里**重新构建**一个 harness,Target 跑**一次**。
- **Harness 组件**(Table 1, §3.2):七个固定的可选组件族:instructions、memory、context organization、composed tools、execution control(controller)、verification & recovery、workspace preparation。由 Builder 决定启用哪些、怎么实现。repo README:未启用的组件为 `null`,启用的是 "bounded policy functions",通过受限解释器执行(不用 Python exec/eval)。
- Builder 工作环境是作者设计的固定框架:共享接口、执行隔离、design guidance、资源限制,interface repair 至多 2 次(§3.2, B.2)。

## 对照问题 a–j

**a. 元学习/共享的是什么?**
一个**自然语言 meta-skill bank**(when/provide/use 三元组,每条 ≤192 tokens),给 Builder 读;不是 harness 代码,也不是代码组件库。Harness 代码每个 test task 现写现用,不跨任务保留(§3.1–3.2,B.1)。Builder 的 prompt/流程本身固定,由作者设计(§3.2 "Builder's Working Environment")。具体的 meta-skill 例子(附录 D):"checkpointing:跟踪产物更新、验证状态、剩余预算,验证通过后尽快结束";"保留原始证据同时限制分析开销";"为提交预留预算";"区分要求的量与测得的观测量";§3.2 的例子:"产物验证后又被编辑 → 版本跟踪 + 重新验证"。

**b. 共享的结构?**
**每个 benchmark × Builder–Target 组合一个扁平的全局 bank**(每个组合 bank 都从空开始,§4.1),测试时按任务做适配:Builder 现建 harness,可选 BM25 top-2 做检索。没有层级、聚类或 soft membership,也**没有建模任务相似度或任务簇**。唯一与"子集"沾边的是 BM25 按 prompt 词面选 ≤2 条 skill,而且它在 5/6 setting 里输给 full bank(§4.2)。作者把"按任务类别/机制看增益差异"(Fig. 4b)只当事后分析。

**c. Harness 是否拆成组件?**
是。七个**固定**组件族(Table 1):instructions / memory / context / composed tools / execution control / verification & recovery / workspace。组件族及其接口固定;每族里具体实现什么由 Builder 每题生成。组件族不是学出来的。

**d. 评测是 held-out tasks 还是 instances?**
**同 benchmark 内的 held-out instances**。按类别/机制分层抽 ~10% 作 development(HB 11/106,NB 32/324),其余作 test(HB 95,NB 292;Table 2,B.1)。作者明说这只验证了 "new instances within known categories and mechanisms",跨数据集和未见任务族留作 future work(A.2, A.3)。只有 2 个 benchmark。NewtonBench 是交互式科学定律发现(Target 设计实验查询、≤10 tool calls,单次实验 ≤20 个查询项;Table 5, D.2),属于信息收集/实验设计;Harness-Bench 是 agent workflow。没有提问/对话式澄清类任务,论文也没有用 partial observability 来定位 benchmark(论文未说明)。

**e. 是否测了迁移矩阵、负迁移、什么因素预测迁移?**
没有组件 × 任务或 harness × 任务矩阵。迁移只沿**模型轴**做(Builder / Target 互换,Fig. 3b,4 个条件,只用 Qwen-Flash 作 Target),出现了一次负的点估计(NB −4.45,CI 含 0)。类别层面有负效应(GPT-OSS vertical workflows −2.23;Fig. 4b)。迁移的预测因素只有定性猜测:"failure modes recur consistently"(§4.2)、"skill granularity"(A.2/A.3 的 hypothesis),没有测量。

**f. 内循环预算、proposer、worker、成本?**
Builder(=proposer)GPT-5.6-Sol,temperature 0、high reasoning;harness 生成 16K output tokens,skill 更新 8K;interface repair ≤2 次。development set 跑 2 遍,每题最多一次 keep/revise/add。注意**测试时每题只建一个 harness,没有 per-task 搜索/迭代**。Target:Gemini-3.6-Flash、Qwen3.8-Flash、GPT-OSS-120B(冻结)。Target 预算:HB 30 turns / 30 tool calls / 96K tokens / 1200 s;NB 12 turns / 10 tool calls / 192K tokens / 3600 s(Table 5)。**Builder 端的 $ 成本、总 token 和墙钟时间都没报**,作者自己把 "gains relative to construction cost" 列为 future work(§6 Message 3,A.3)。

**g. Baselines 与主数字**
见上面"结果"一节:native 51.40 / no-skill Builder 56.36 / Direct Builder skills 53.29 / Independent Structured Target skills 54.38 / Mined Free-form 51.23 / Ours all 65.31(macro,Table 3)。**没有和 Meta-Harness、ADAS、AFlow、DGM、ACE、Evo-Harness 等方法直接对比**,这些只出现在 related work。

**h. 泄漏/过拟合/reward hacking 控制**
- dev/test 分开,bank 在测试前冻结,"no revisions based on test outcomes"(B.1)。
- 测试时 Builder 看不到 test 轨迹、分数、参考答案和 evaluator 内部(B.1,A.2)。
- 学习时不给 private reference answers,也不给研究者写的诊断(B.1);但会给 "benchmark-native development score"(§3.1)。
- **没有单独的 validation/selection split**(B.1 原话 "We use no separate validation partition");是否保留第 2 遍 bank 也没有选择机制,作者在 §5.1 承认应加入 rollback。
- 构建失败记 0 分,分母固定(B.3)。
- 不确定性:20K 次配对 task bootstrap,未做多重比较校正,且每个条件**只有一次执行**,不反映生成随机性(B.3, §6)。
- 没有讨论 reward hacking。harness 中的 auditor/submission gate 只检查格式和一致性;是否会针对 evaluator 写 checker,论文未说明。repo README 提到 interface repair "do not use Target scores to select candidates"。

**i. 代码/数据**
https://github.com/qiancheng-apodex/MetaSkill-AI4AI(已核实公开)。README 自述:包含七组件运行时、受限解释器、Builder build/run/learn/refine CLI,以及 OpenAI 和 Anthropic 客户端;**不包含论文完整的实验调度器和 BM25 检索流水线**。论文 A.2 又写 "Upon paper acceptance, we will release the full code and all prompts",与首页脚注 "code is released" 不完全一致。learned bank 和轨迹是否公开,论文未说明。

**j. 自述局限与未来工作**
只有一个主 Builder、两个 benchmark,每个任务×条件只执行一次(§6 Message 3);没评估收益相对构建成本的性价比;泛化只到同 benchmark 内的新实例,跨数据集、未见任务族和不同工具接口是 next step(A.2, A.3);精炼非单调,需要基于 dev 的置信评估、保留与回滚(§5.1, A.3);需要更长的任务流、更大的 bank、自适应检索和 skill 组合(A.3);考虑 skill 互补性和 Target 反应的检索(§4.2);recipient 端反馈来细化迁移的 skill(§6 Message 2);Builder 学习与 Target 自身改进结合(A.3);联合分配 learning/construction/execution 的计算或延迟预算(A.3);独立的学习重复、多次执行、其他划分,以及针对单条 principle 的干预式因果分析(A.3)。

## 与我们的区别

我们的计划:冻结 Qwen3.5-9B,~17 个主动推理/部分可观测文本 benchmark(~100 subtasks);内循环是 Opus proposer 做 Meta-Harness 式的 per-task harness 代码进化;外循环是 hierarchical Reptile,把反复出现的代码 edit 提升为共享组件,并用连续(fuzzy)task membership 实现任务子集间的部分共享;在 held-out tasks 上评测并画 adaptation curve;科学问题是迁移结构是否沿信息收集问题的维度(hypothesis space / observation channel / cost / stopping)分布,而不是沿 benchmark 身份分布。

**本文已经做了的(与我们重叠)**
1. 冻结 Target + 强模型 Builder/proposer 写 harness 代码、权重不动:与我们的设定同构。
2. "把跨任务的执行经验沉淀成可复用知识,用来指导新任务 harness 构建":正是我们外循环的动机句。审稿人会直接说 "this is MetaSkill-AI4AI"。
3. 固定组件槽位(七个组件族)+ 组件消融:与我们"共享组件"的说法在概念上相邻。
4. 在 NewtonBench(交互式实验设计、预算受限)上有信息收集类任务的结果,而且他们学到的 meta-skill 里就有 "为提交预留预算"、"区分观测量与目标量",这些与我们的 cost / stopping / observation channel 维度相近。
5. dev 学 → 冻结 → held-out 测的协议,以及 refinement passes 曲线(Fig. 2)。

**本文没做的(我们的空间)**
1. 共享的是**自然语言原则**,不是**代码**;每题 harness 现写现扔,没有任何代码层面的跨任务复用或"提升 edit 为共享组件"。
2. 共享结构是扁平全局 bank(每个 benchmark 一个),**没有层级、没有 soft/fuzzy membership、没有任务相似度建模**;唯一的子集选择是 BM25 top-2,还输给 full bank。
3. **没有 per-task 内循环搜索**:测试时每题一次构建、一次执行,而非 Meta-Harness 式的多轮迭代。
4. **held-out 只是同 benchmark 的实例**,跨 benchmark 和未见任务族被明确列为 future work(A.2/A.3)。我们的 held-out tasks + adaptation curve 正好补这里。
5. 没有任务 × 组件迁移矩阵,也没有负迁移的系统测量,对"什么预测迁移"只有一句 granularity 的猜想。我们的科学问题(迁移是否沿信息收集维度而非 benchmark 身份)他们完全没有碰。
6. 只有 2 个 benchmark,没有提问/澄清类、部分可观测对话类任务,也没有小开源 9B 级别的 Target(GPT-OSS-120B 是最小的)。
7. 不报 Builder 成本。

**审稿人可能的攻击与应对**
- "跨任务复用 harness 设计经验已被 MetaSkill-AI4AI 做过(还有 Evo-Harness 2608.15071、Meta Context Engineering 2601.21557、MetaSkill-Evolve 2607.05297),你们只是换了表示。" 应对:把贡献点放在 (i) 代码级共享 + 部分共享结构,(ii) 跨任务族 held-out,(iii) 迁移结构的科学发现;正文要和他们的 "flat NL bank + BM25" 做**正面对比实验**(把它当 baseline:同 proposer,把我们的轨迹喂给 when/provide/use bank,full-bank 注入)。
- "fuzzy membership 有必要吗?他们 full bank 已经胜过稀疏检索(5/6)。" 应对:必须给出 flat-global vs task-specific vs fuzzy partial sharing 的消融,并展示负迁移确实存在(他们自己也有 GPT-OSS vertical −2.23、跨 Builder NB −4.45 的迹象,可以引用作为 motivation)。
- "Reptile over code edits 只是 meta-skill bank 的代码版。" 应对:强调他们的 bank 学习没有选择集,也没有回滚(他们自己承认非单调),而我们的外循环有明确的跨任务目标和 held-out task 选择。
- "信息收集维度的解释是事后贴标签。" 他们没做这个,所以这是我们最独有的部分;但需要预注册维度标注并与 benchmark-identity 聚类做对照,否则容易被说成 post-hoc。

**结论**:本文覆盖了我们 story 的"动机层"(把 harness 经验跨任务复用),而且同是冻结 Target、强 Builder;在"结构层"(代码级、部分/模糊共享、层级)、"评测层"(跨任务族 held-out、adaptation curve、迁移矩阵)和"科学问题层"(迁移是否沿 information-gathering 维度)上没有重叠。论文必须引用它,并把它作为 baseline 来跑。
