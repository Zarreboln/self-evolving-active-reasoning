## 任务

在一个 open-world task stream 上(任务逐个到达、没有 ground-truth answer、没有 labeled validation feedback),给 frozen model 自动改 harness(§2.1)。harness = K=8 个可编辑文件组件(沿用 AHE 的 file-level decomposition 再加一个 plugin)。允许在 bounded budget 内对**当前任务**重复执行,但已完成任务不能 replay(App. A.1 "Streaming")。评测是三套"专业交付物"benchmark:WorkBuddy-Bench(Code/Web/Office)、JobBench、Harvey LAB(法律)(§3.1, App. B)。

## 问题

两点(§1):
1. open-world 任务部署前没见过,没有 ground-truth verifier,在线改 harness 缺可靠信号;
2. 现有 harness RSI 高度 task-specific,改好当前任务的 harness 不会让**下一个任务的改进过程**变好;直接继承上一个任务高度定制的 execution harness 会在分布漂移下带来噪声。
核心问题原文:"Can recursive self-improvement improve both the current harness and how future harnesses are improved?"

## 方法

两层 recursion(§2,Fig. 3):

- **Task-level recursion**(改 execution harness,§2.2)。基本单元是 contrastive **Propose–Probe–Compose** step(Eq. 1):
  - Propose:先跑参考执行 e0;按两个 scope 各出一个候选:**invariant**(planning/tool use/context management/delegation 这类跨域 agentic 缺陷)和 **domain-specific**(当前领域的知识、流程、约束)。
  - Probe:候选在同一任务、同模型同环境下各跑一次,与参考做 behavioral contrast(不判对错)。
  - Compose:读参考、候选、diff、全部执行证据,选择性 merge / 采纳一个 / KEEP_BASE,每个决定绑定具体 trajectory 时刻。
  - 扩展:parallel recursion(k 个参考执行、k 个 INV + k 个 DOM 候选、k 个独立 composer,Eq. 2;"one population update; k controls its width rather than its depth")和 sequential recursion(k 步串联,Eq. 3)。k>1 时用 blind agentic selector 在匿名交付物里选一个(Prompt 5),对应 harness 记为 H*_t。
- **Harnessing-level recursion**(改 improvement harness R_t,§2.3)。任务结束后 Reflector(Prompt 6)对每个被改组件写 helped/hurt/no observed effect/confounded 的归因行,至多写一条 cue/lesson/evidence/confidence 的 experience;R_{t+1}=Update(R_t, H*_t, D_t)(Eq. 4)。库条目 = 被采纳的完整 harness 树 + EXPERIENCE.md,配 index,后续 session 按需读(App. D.2)。下一任务仍从共同的 H0 起步,不自动继承,库里的组件只在 Propose 时被选择性 reuse/adapt。
- 什么固定:"Model weights, stage instructions, and the decision rule remain fixed, while the library evolves"(§2.3)。也就是说被"递归"更新的只有这个库(adopted harness + lessons),editor 的 prompt 和算法不变。
- 实现:executor = Gemini 3.5 Flash / GLM-5,外壳 OpenCode / Codex(4 种配置);editor 和 selector = Claude Opus 4.8,在 OpenCode 下 high reasoning effort(§3.1, App. D.2)。主表 k=1,"+ Recursion" 为 parallel k=5。

## 结果

- 单步(k=1)在全部 4 配置 × 3 benchmark 都超过 base:WorkBuddy 最大 +11.5(GLM-5/OpenCode 64.2→75.7),JobBench 最大 +4.5(Gemini/OpenCode 31.5→36.0),LAB Partial 最大 +11.8pp(GLM-5/OpenCode 59.6→71.4)(Tables 1–2, §3.2)。
- parallel k=5 再加:WorkBuddy +2.9~+3.9,JobBench +3.0~+4.2,LAB +2.6~+6.7pp(§3.2)。
- 对比 baseline:WorkBuddy Avg. 和 JobBench Score 在 4 配置全赢;LAB 上 Gemini/Codex 由 Meta-Harness 领先(76.5 vs 75.6)(§3.2, Table 2)。
- budget 曲线:WB-code parallel 76.5→80.8,WB-office 79.5→83.4(k=1→5,Fig. 5);两种 recursion 在 k=2 已超过所有 baseline 的 k=5。
- 消融(Gemini/OpenCode,k=1,Table 3):Full 77.5/36.0;w/o library 74.4/34.2;w/o scoping 74.6/32.3;w/o composition 75.9/34.1(WorkBuddy/JobBench)。
- 库迁移:JobBench 库→WorkBuddy 单步 +0.6/+0.5/+2.9(Code/Web/Office,Fig. 7 右);LOO 重跑 77.5→79.4、36.0→37.7(Fig. 11,作者明说是 offline reuse 分析,不是 online 增益)。

## 对照问题 a–j

**a. 跨任务共享/meta-learn 的是什么?**
一个 **harness improvement library**(作为 improvement harness R_t 的可变部分):每个已完成任务被采纳的**完整 harness 代码树** + 一份 EXPERIENCE.md(cue/lesson/evidence/confidence)+ index(§2.3, App. D.2, Prompt 6)。editor/composer/selector 的 prompt、算法、决策规则、模型权重都固定(§2.3 原句;App. A.1 "Model weights and the improvement algorithm remain fixed")。所谓 "recursive" 具体是:task-level 改 execution harness;harnessing-level 改"指导改 harness 的那个东西",但这个东西实际只是一个检索型示例+经验库,不是会写 harness 的代码被改写(不像 STOP/Hyperagents 改 improver 本身)。另外,每个新任务都从共同的 H0 起步,不继承上一任务的 harness(§2.3)。

**b. 共享的结构?**
平的、按领域划分的库:"Each benchmark domain has its own library directory"(App. D.2),index 由 editor agent 自己按需翻,**没有**层次、聚类、soft membership,也**没有**任务相似度建模(检索全靠 agentic editor 自己读 index;只有 baseline ReasoningBank 用 embedding 相似度,App. C)。唯一像"部分共享"的是 Propose 的两个 scope:**invariant**(假设跨域复发)vs **domain-specific**(当前领域),由 prompt 硬编码成两个 editor 角色(§2.2.1, Prompts 1–2),属于二分,不是连续的。消融 w/o scoping 在 WB/JB 上掉 2.9/3.7(Table 3)。跨 benchmark 只测了 JobBench→WorkBuddy 一个方向(Fig. 7 右)。

**c. harness 有没有分组件?**
有。K=8 个文件组件,**固定**(人定的):C1 system prompt、C2 guardrails、C3 memory(LongTermMEMORY.md)、C4 tool guidance、C5 subagents、C6 skills、C7 scripts、C8 plugin(TypeScript,在 tool loop 内挂钩);沿用 AHE 的分解加一个 plugin(§2.1, Fig. 2, Table 5)。组件的**内容**由 editor 学;组件集合本身不学。Prompt 1 还给了形式偏好顺序(skill > script > subagent > plugin > always-on text)。编辑分布:skills+scripts 约占每个 benchmark 编辑量的一半(Fig. 10 右, App. E.2)。

**d. 评测:held-out tasks 还是 held-out instances?**
基本是**同一 benchmark/领域内的新实例流**:每个 benchmark 一个 test stream,库从空开始、任务逐个处理(§3.1)。注意 harness 是在**被评测的那个任务上**改出来的(transductive:用当前任务的多次执行改 harness,再交付当前任务的输出),所以严格说没有"held-out 任务上测 adaptation"。任务数:WorkBuddy test 40/35/25(Code/Web/Office,按 category 对半切),JobBench 34 test(31/34 frozen split),LAB 100 test(App. B)。唯一"未见领域"的证据是 JobBench 库→WorkBuddy(Fig. 7 右)。**没有** interactive / partially observable / 向人提问类任务;都是交付物生成(代码、网页、Office 文件、法律文书),agent 有文件检查、web search 等工具探索,但不是信息获取型推理任务。

**e. transfer matrix / negative transfer / 什么预测迁移?**
都没有。有的只是:库 provenance 统计(修改文件中 22%(LAB、WB-office)到 47%(JobBench)带库来源,只有 2–10% 保留一半以上行,Fig. 10 左);LOO(Fig. 11);一个方向的跨 benchmark(Fig. 7 右);跨 executor 迁移(Fig. 12:Gemini 3.5 Flash 上改出的 harness 给 GLM-5 Code 58.5→75.8 即 +17.3,Gemini 3.7 Flash +0.3/+6.4,Opus 4.8 +2.6/+1.1,Code/Office)。没有组件×任务矩阵,没有负迁移度量,没有迁移预测因子。Limitations 里明说行为对比 "do not ... establish that an adopted change will transfer to a different task"(App. F)。Fig. 14 的 9 个回退案例里有"错误前提在候选间传播"一类,但属任务内,不是跨任务负迁移度量。

**f. 预算、proposer、worker、算力**
- 内循环预算 k ∈ {1..5}(主表 k=1,+Recursion k=5;Fig. 5 扫 1–5)。每次 rollout 上限 200 model turns、3,600 秒(WorkBuddy 用 2× benchmark 默认容器超时)(App. D.1)。
- proposer/editor/composer/selector/reflector = Claude Opus 4.8,OpenCode 下 high reasoning effort(App. D.2);same-model 实验(OpenCode,k=2)五个模型从 GLM-5 到 Claude Opus 5 自改自用(Fig. 8)。
- frozen worker:Gemini 3.5 Flash、GLM-5 × OpenCode、Codex(§3.1);跨 executor 迁移另测 Gemini 3.7 Flash、Opus 4.8(Fig. 12)。
- 算力:Fig. 6 按"提交前花的全部 tokens(执行+改进)"给每任务 M tokens 的 Pareto 图,JobBench 横轴约 10¹–10² M tokens、WorkBuddy 约 10⁰–10¹ M tokens(对数轴,读图,非原文数值);Gemini/OpenCode k 1→5 增益 4.5→7.5(JB)、5.1→8.4(WB);Meta-Harness 比 k=5 的 Harness² 花更多算力、分数更低。具体 token 数值、美元成本、wall-clock:论文未说明。

**h. 泄漏/过拟合/reward hacking 控制**
- 工作目录守卫:含 grader verdict、rubric 或 score 的目录一律拒绝交给 session(App. D.2);所有 prompt 声明"没有 rubric/score",禁止揣测 grader(Prompts 1–6)。
- WorkBuddy verifier 不向 pipeline 内任何模型暴露期望值;JobBench rubric 不给 executor/editor/selector(App. B)。
- 选择:blind selector,匿名、打乱、看不到 harness,也不允许合成新内容(§2.2.2, Prompt 5)。
- 训练半区只给 Meta-Harness 用;Harness² 与其他 baseline 只走 test stream,库从空开始;不 replay 完成任务(App. B, A.1)。
- Reflector 偏好标 confounded,"adoption alone never establishes that an edit helped"(Prompt 6)。
- LOO 被作者明确标为 retrospective(可看到后续任务的条目),不算 online 增益(§4, App. E.2)。
- 评测侧:WorkBuddy 判官 = Gemini 3.5 Flash(与 executor 之一同模型);JobBench 判官 = Claude Opus 4.8(与 editor/selector 同模型);LAB 判官 = Claude Sonnet 4.6(App. B)。**[我们的观察,论文未讨论]** JobBench 上 editor/selector 与 judge 同为 Opus 4.8,可能有 self-preference;另外 harness 在被评测的同一任务上改,且 Prompt 1 明确鼓励把"本工作区已验证的事实"写进 harness,属于 transductive 适配,不是在 held-out 任务上泛化。

github.com/google-research/harness2(论文首页,Prompt 部分说各 benchmark 专属 prompt 块 "are in the code release");repo 实测存在(2026-10-06 创建,2026-11-02 最近 push)。项目页 harness2.github.io(HTTP 200)。

**j. 自述局限与未来方向**
- Limitations(App. F):(1)recursive refinement 的额外执行和 editor 成本,只刻画了有界预算范围,没有找到普适最优分配;(2)无 ground truth 时依赖 behavioral contrast + model judgment,对执行随机性和 shared model bias 敏感,不保证正确,也不保证被采纳的改动能迁移到别的任务。
- Future(App. G):(1)管理 improvement harness:库变大后合并重叠组件、修订过时经验、按当前任务改进检索;(2)adaptive recursion:按难度和先验经验相关性分配探索,无新证据时停止。
- Failure analysis(App. E.6, Fig. 14):blind selection 选错(96→55)、错误前提在候选间传播、判官崩溃/结果方差。

## 与我们的区别

我们的计划:frozen Qwen3.5-9B;约 17 个文本 active-reasoning benchmark(约 100 subtask,部分可观测);内循环 = Meta-Harness 式每任务 harness 代码进化(Opus proposer);外循环 = 对代码编辑做层次化 Reptile,把反复出现的编辑提升为共享组件,任务成员关系是**连续(fuzzy)**的,也就是允许在任务子集之间部分共享;在 held-out tasks 上画 adaptation curve;科学问题:迁移结构是否沿信息获取问题的维度(假设空间、观测通道、代价、停止)而不是 benchmark 身份。

**它已经做了的(与我们重叠):**
1. "改 harness 的同时积累跨任务可复用的改进经验"这一主线:per-task 内循环 + 跨任务库,框架上就是 inner/outer 两层,还起名 recursive。
2. 跨任务复用以**可执行组件**为单位(完整 harness 树,"Executable components are retained rather than summarised as prose",App. D.2),并量了组件 provenance(reused/adapted/fresh,Fig. 10)。我们"把重复编辑提升为共享组件"在直觉层面与此相近。
3. 固定的组件槽位分解(8 个文件组件)以及按组件分析编辑落点。
4. 一个二分的"共享 vs 领域"结构:invariant vs domain-specific 两个 scope(且消融有效,Table 3)。审稿人会说这就是"global vs task-specific"的一个版本。
5. frozen executor + 强 editor、same-model、跨 executor 迁移,label-free 控制(守卫、blind selector)。

**它没有做的(我们的空间):**
1. **没有显式的共享结构学习**:库是按领域分目录的平铺 + agent 自己翻 index;没有 Reptile/元梯度式的聚合,没有"重复出现的编辑被提升为组件"的机制(复用是 editor 每次看库时临时决定的,不更新任何共享参数或共享代码基线;每个任务都从 H0 起步)。
2. **没有连续/模糊的任务成员关系、聚类或层次**,也没有任务相似度建模;sharing 只有 invariant/domain 二分 + 领域目录。
3. **没有 held-out task 上的 adaptation curve**:他们在被评测的那个任务上 transductive 地改;唯一跨域证据是单方向 JB→WB 的三个数(+0.6/+0.5/+2.9)。
4. **没有 transfer matrix、负迁移度量、迁移预测因子**;作者在 Limitations 里自己承认不保证迁移。我们的科学问题(迁移结构沿信息获取维度而非 benchmark 身份)他们完全没碰。
5. **任务性质完全不同**:他们是长程交付物生成(代码/Office/法律),判官打分;没有 partial observability、提问、信息获取、停止决策;executor 是大的闭源/前沿模型(Gemini 3.5 Flash、GLM-5),不是 9B 小模型。
6. 规模:3 个 benchmark(WB 拆成 3 个领域),约 234 个测试任务;我们是约 17 个 benchmark、约 100 个 subtask,任务族多样性高得多,才有可能估计迁移结构。

**审稿人会怎么拿它攻击我们的 novelty:**
- "两层(per-task harness 进化 + 跨任务改进经验库)已由 Harness² 提出,并且是 label-free、streaming 的;你们的外循环只是换了个聚合方式。" 回应:我们的贡献要放在**共享结构本身**(连续成员关系的部分共享 vs 他们的平铺库 + 二分 scope)和**迁移结构的科学结论**上,而不是"能跨任务复用"这件事;要做 head-to-head:Harness² 式库(平铺 + invariant/domain 二分)作 baseline,证明 fuzzy 部分共享在 held-out tasks 上更好、负迁移更少。
- "invariant vs domain-specific 已经是 shared + task-specific 分解,而且有消融。" 回应:要展示二分不够,即存在只在部分任务子集上共享的组件(比如只对"假设空间大"的任务有效的提问策略),并且 fuzzy membership 能抓到、二分抓不到。最好把成员度与信息获取维度挂钩,并给出可视化的 transfer matrix。
- "Harness² 已证明组件(skills/scripts)是复用主体(Fig. 10)。" 回应:他们只统计 provenance,不证明复用组件带来增益,也不测负迁移;我们要报组件×任务的增益矩阵。
- "你们用 Meta-Harness 式内循环需要标签/评分,Harness² label-free。" 这是口径风险。我们的 AR 线口径是 label-free/transductive(见 project_ar_claim_scope_data_free),要么明确内循环用什么信号,要么准备 label-free 变体对照,否则会被说"用了更强监督还只做到类似的事"。
- "他们 transductive 地在测试任务上改,你们在 held-out 任务上评测,设定不同,不可比"。这反过来可以作为我们的卖点:我们测的是迁移到**未见任务**的 adaptation curve,这是他们没做的。但审稿人可能要求我们也报 Harness² 在我们设定上的数字,需要预留算力。
