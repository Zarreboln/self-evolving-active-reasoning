## 任务

在安全代码生成上做 harness 自进化。每道题 t_n=(x_n, p_n):x_n 是任务描述,p_n 是安全策略(PoC exploit),解题时看不到 p_n,只有评测 oracle 用到它(§3)。两个目标都是执行得出的通过率:f_func=单元测试通过率,f_sec=PoC exploit 被挡住的比例(附录 B 式 9–11)。主指标是 secure-pass@1 = F∧S,即同一条轨迹既功能正确又安全(式 1)。搜索时优化的是两个边际量 (f_func, f_sec),不直接优化 F∧S;理由是 Fréchet 界(式 2)以及"边际量能告诉 proposer 是哪个性质失败了"(§3)。

## 问题

作者指出现有 harness 自进化方法(ADAS、DGM、Meta-Harness、Self-Harness 等)有两个缺陷(§1、§2):
1. **单目标**:只优化 pass rate 这种标量,安全性没有被当作独立的轴。加权求和会漏掉非凸 Pareto 区域,还会"拿一个目标的分去换另一个目标更便宜的分";硬约束只把问题变成带约束的单目标搜索。
2. **整体式进化(monolithic)**:每一代把整个仓库当一块来改写,反馈只来自一个环境,"do not disentangle general harness design from environment-specific adaptation"(§1)。可迁移的设计和针对 benchmark 的适配拿到同样的奖励信号,混在同一份 harness 里。作者举的例子:在容器里构建和执行代码是通用能力,而镜像选择、清理策略、benchmark 的 sandbox 约定是环境相关的。

## 方法

整体流程见 Fig. 1,包括三部分:

- **(a) 多目标分解 = MOEA/D**(§4.1):N 个权重向量 λ_i 均匀铺在 func–sec 单纯形上,每个子问题维护一个 incumbent harness,用加权 Tchebycheff 标量化 g^te(H|λ_i,z*)=max_j λ_ij (z*_j − f̂_j(H))(式 4),z* 是到目前为止每个目标的最好值。变异是单亲的:子问题 i 的孩子只从自己的 incumbent 产生;如果某子问题停滞(父代和失败摘要都没变),改从邻居里按 λ_i 最好的那个繁殖。孩子可以替换邻域 B(i)(T 个最近权重向量)里的 incumbent,替换数上限 n_r=2(式 6)。作者强调这样做"diversified by construction"选择压力,不需要手工设计代码级多样性指标;proposer 每次只看一个完整父仓库,上下文有界。最后交付的 harness 按式 3 选:在**搜索集**上 max min(f̂_func, f̂_sec),平局取早一代。
- **(b) 因子化进化**(§4.2,附录 E):沿两个维度分解,"component type and adaptation scope"。
  - 组件类 K = {tools, skills, logic}(logic 包含 orchestration)。
  - 作用域 Σ = {gen, env}。
  - 流程:diagnose → hypothesis → 选组件类 k_i → 用 R_{k_i} 决定作用域 s_i(式 7)→ 用算子 O_{k,s} 改 harness。每个孩子通常串行应用一个最长 8 步的算子计划 Π(式 13–14,E.1)。
  - 另有一个跨作用域的 **generalize 算子**(E.3):只重新归档现有组件,不加新能力。动作分 Promote / Demote / Derive 三种,每次只纠正一个归错的单元。
  - 孩子在评测前要过三段 smoke test(E.5),失败给一次修复机会。
- **(c) 推理时动态组合**(§4.3,附录 F):加载时只 import `general/` 和当前环境的目录;然后由一个 LLM planner 读"已注册 workflow step 菜单"加任务描述,为**每道题**生成一个 DAG(式 8),节点是 generate、build_verify、endpoint_check、security_audit、shell_probe、edit_fix 等 step,可以带 `when` 条件边。组合 agent "does not modify the evolved components; it only determines which components to activate"(§4.3)。
- **Harness 结构**(Fig. 4):一个自包含的 Python 包,`config/ orchestrator/ steps/ tools/ skills/ prompts/ utils/`,"each directory = general/ + <benchmark>/"。评测器只 import 入口 `AgentHarness`;包里的一切,包括 LLM 调用层,都可以进化。种子 H_0 是轻量 ReAct(读文件、写文件、命令行,加一个简单 orchestrator;附录 E)。

## 对照问题 a–j

**a. 共享/迁移的是什么?**
**真代码**:harness 仓库里每个组件目录下的 `general/` 部分(tools、skills、logic/orchestrator/steps、prompts、utils)。跨 benchmark 迁移时"only the general scope is loaded on the target benchmark, so benchmark-specific fixes do not carry over"(§5.2;附录 F:"H^env_{e'} is empty, so only H^gen transfers")。另外,LLM planner 本身也是 harness 的一部分,会一起迁移,它负责在新任务上按题组合 step。没有自然语言的经验库;skill 是 `.py` 模块,包含触发条件、简短通用流程和一个例子(Table 4)。

**b. 结构:通用机制/benchmark 适配怎样表示、怎样进化、推理时怎样组合?是不是严格两层?**
- **表示**:是目录级的两层。每个组件目录都拆成 `general/` 和 `<benchmark>/`(Fig. 4)。benchmark 作用域里的模块"**shadows the general module of the same name**, so benchmark-specific behavior overrides the general default without modifying it"(E.2)。这实际上是**单继承、按模块名覆盖**的两层结构。作者说这种区分"operational rather than semantic"(§4.2),并且"we do not impose a rigid file-level partition"(F.2)。
- **进化**:每次编辑前,先由 `decide_scope` 做一次只读的小模型调用,只回答一个问题:"**can the agent derive the relevant fact at run time on its own?**"能就放 general,如果是评测器或交付通道的固有规则就放 benchmark 作用域。作用域会被编译成写白名单,在工具层强制执行,越界写入会被回滚;`decide_scope` 调用失败时默认放 general(E.2)。general 作用域禁止硬编码端口号、框架名、CWE 列表等;benchmark 作用域的文件要在头部注明目标 benchmark。边界本身由 `generalize` 算子(Promote/Demote/Derive)不断调整,它要满足两个不变量:(i) 在当前 benchmark 上行为等价;(ii) 只加载 general 部分也必须能跑(E.3)。
- **组合**:分两步(附录 F)。先做 scope loading,得到 general 加当前环境的组件池;再做 task-level planning,由 LLM planner 从 step 菜单里**每道题**生成一个 DAG,以拓扑序执行,最多 16 个节点(Table 8 注)。
- **是不是严格两层**:**是**。Σ = {gen, env},只有两个取值。没有更细的层级,没有"若干 benchmark 共享、其他不共享"的部分共享,也没有多父继承。而且**每个进化 run 只针对一个 benchmark**("evolve a separate harness population on each benchmark",§5),所以一个进化出来的 harness 实际上只有一个 `<benchmark>/` 目录。"general"是按"运行时能否自行获取该事实"这条规则**预判**出来的,不是由 ≥2 个 benchmark 共同使用来证实的。跨 benchmark 的"通用"只在事后用零样本迁移检验过(Table 12)。作者明确说这个分解是 "inductive bias; we do not assume that either decomposition is unique or theoretically exact"(§4.2)。

**c. Harness 分解**
有两个正交维度(§4.2):组件类 {tools, skills, logic},以及作用域 {gen, env}。对应三个算子 tool / skill / logic,各自只能写自己的目录(Table 4):tool → `tools/ utils/ (config/)`;skill → `skills/ prompts/`;logic → `steps/ orchestrator/`,在 general 作用域还可以改包根部的 loop 模块。对每个算子的交付物都有硬性要求,例如 tool 算子"Phantom verification is explicitly forbidden";skill 算子禁止写"默认行为 + 例外条款"式的 skill,因为作者实测有一个这样的 skill 修好了目标题,却弄坏了另外两道题;logic 算子不允许靠改 prompt 实现控制流的效果。从包结构看(Fig. 4),还有 config、prompts、utils 等目录。

**d. Held-out 任务还是实例?general 部分能否迁移到没见过的 benchmark?**
- benchmark 内部:evolve / held-out-IN / held-out-OUT,SecRepo 各 30 题,Bax 各 28 题(§5)。按 Table 14,"IN = crash-type families seen during search; OUT = unseen families",所以 OUT 是**同一 benchmark 内没见过的漏洞类型族**。BaxBench 的 IN/OUT 怎么划分,论文没有具体说明。
- **跨 benchmark**:有。SecRepo↔Bax 双向零样本迁移,只加载 general(Table 12),HH 都高于 baseline,Meta-harness 都低于 baseline。还有 Bax→CWEval(Table 11),任务格式也变了,并且包含源 benchmark 没有的语言。这说明 **general 部分确实在没见过的 benchmark 上起作用**,但只有 2 个 benchmark 加 1 个迁移目标,而且全部属于安全代码生成这一个领域,目标函数相同("generalizes across benchmarks with identical dual objectives",§1)。跨领域迁移被作者列为 open(附录 I "Scope")。

**e. 迁移和负迁移是否测量?**
- 有一个 2×2 的 optimized-on × evaluated-on 矩阵(Fig. 3 / Table 12),但只在 benchmark 粒度上,没有组件 × 任务矩阵。
- 负迁移的证据:Meta-harness 跨 benchmark 迁移时低于 baseline(39.3 < 42.9,36.7 < 46.7);Table 1 中 func-only 在 OUT 上安全增益保留率为负(−103%/−197%);CWEval 上功能通过率在 3/5 种语言下降(F&S 仍然上升);DGM 产生硬编码搜索集崩溃分布的孩子,如 `_OOW_LADDER`(K.6)。
- HH 自身在 Table 12 上没有出现负迁移。论文**没有**分析哪些 general 组件在迁移中有用、哪些有害,也没有逐组件做迁移归因。

**f. 预算、模型、成本;多目标是什么?cost 算不算一个目标?**
- 模型:"both the harness proposer and the underlying task-solving agent use gemini-3.6-flash"(§5)。**proposer 和解题模型是同一个模型**,不是强 designer 配弱 worker。K.7 的校准 baseline 里出现了 SWE-agent(Opus)和 Terminus-2(Gemini)。
- 目标:**只有 functionality 和 security 两个**(m=2),式 9–11。**cost/token 不是目标**。
- 预算:主方法的 N、T、代数**正文没给**。只有分析 run 给了:MOEA/D 单独跑是 N=5、T=2、3 代(G.1);BaxBench 一个 run 是 N=6、4 代、2 个种子、24 个孩子(Fig. 6)。每题的采样数 K(式 11)也没给。Table 2 说各方法用"same ... token budget",但具体数值没有报。
- 成本:只报了**解题时**每题的 token(Table 8:baseline 31,902;固定流水线 58,230;动态 63,064)。**proposer 的 token、$ 和墙钟时间都没报**。附录 I 的 Cost 只有一句:"Real Docker build/exploit evaluation dominates wall-clock"。过拟合门校准的成本是 240 次 judge 调用加 35 次 held-out 评测(K.5)。

**g. Baselines 与主数字**
Baseline(未进化)、Meta-harness 三个变体、DGM(标量化)。这两个方法都"run from their authors' released code"(附录 C),不是重新实现。另有 Table 2 里的 7 种多目标聚合策略。K.7 里有 SWE-agent(Opus)0.444 和 Terminus-2 进化版 0.556,作为校准参考。主数字见"结果"一节:HH 在 SecRepo 上平均 F&S 76.7,对比最强 baseline 51.1;在 Bax 上 61.3 对比 52.4。没有和 ADAS、AFlow、GEPA 等方法做实验对比;GEPA 和 ADAS 被称为"conceptual predecessors",作者说只借鉴了想法,没有用它们的算法或代码(§2)。

**h. 泄漏、过拟合、reward hacking 控制**
- held-out 两个 split "remain inaccessible to the proposer and selection procedure"(§5);交付 harness 的选择只用搜索集(式 3)。
- diagnose 阶段有 **evidence-integrity gate**:引用的路径必须存在于当前父代自己的 eval-artifact 树里,引文(**≥24 字符**)空白归一化后必须在原文中逐字出现;验证不过就重试一次,仍然不过则丢弃这份指导,让算子在没有指导的情况下继续(E.1)。
- **overfitting gate**(附录 K):一个 one-shot LLM judge 看 parent→child diff,输出风险分 ρ∈[0,1],超过阈值 θ 就拒绝。校准方法是在真实孩子里注入已知过拟合,共三个层级 11 种,另有 4 种"看起来可疑但其实通用"的对照(Table 18),用配对 McNemar 检验。**但 K.5 只写了实验设计,没有报检出率、误报率,θ 的具体值也没给**。
- 评分文件保护:每次评测在隔离的 Harbor 容器里跑,断网,有资源上限;`solution/` 和 held-out 不进镜像;evaluator、任务定义、测试在每次算子调用前做快照,调用后强制恢复(K.6)。作者实测过,不加这层保护时 agent 会直接去改 `evaluate.py`,并指出 Meta-harness 的代码里没有这层保护。
- 三段验证里有一条:父代已有的具名 self-test 断言在孩子里必须还在,防止靠删测试来过关(E.5 Stage 3)。
- 局限:每个 split 只有 30/28 题,没有置信区间,也没有显著性检验。基础设施失败的题会从当次 run 中剔除,所以分母会变(附录 C)。作者用"we do not see this signature in our own runs"来论证 generalize 算子防止了硬编码,这是定性说法,没有量化。

**i. 代码/数据**
没有发布,论文中也没有承诺。数据是三个公开 benchmark。进化出来的 harness、轨迹、diversity 分析工具都没有公开(附录 J 描述了工具的命令行参数,但没有给链接)。

**j. 局限(作者自述 + 我看到的)**
- 自述(附录 I):在 SecRepoBench 上 Pareto 前沿很窄,"better scaffolds often improve functionality and security together",所以 Tchebycheff 的价值主要在搜索方向,而不是找回非凸区域;真正有冲突的场景(对抗、注入、修安全导致老测试失败)是下一步。只在安全代码领域做过。没测 shielded evolution。成本主要被 Docker 评测占据。附录 J 说代码多样性指标和行为几乎不相关(r=+0.030),多样性应该从行为上度量。
- 我看到的:每个 split 28–30 题,generalize 消融只用 6 题;主方法的进化预算和 proposer 成本没报;overfitting gate 没给结果;CWEval 的对照不是同一个 baseline;"general"作用域由单一 benchmark 的进化产生,判据是一个 LLM 调用回答"运行时能否获取";proposer 和 solver 是同一个模型。

## 与我们的区别

我们的方法:把完整 agent harness(冻结 LLM 外围的 prompt、memory、控制流、解析等代码)分解成一个 soft hierarchy,供新任务复用。harness 可以来自任何来源(Meta-Harness 进化的或人写的),必须先过质量门(明显优于 base agent),然后逐个任务纳入。Opus 依据 3 条 base-agent 轨迹写任务描述、能力和 profile,再写 harness 的描述,然后做一次 review,把共享功能提炼成 `module` 节点和 `workflow` 节点。节点之间组成多父 DAG,每个节点有真代码、描述、父节点和成员任务,每个成员都要附可核验的证据(函数名或 ≥40 字符的逐字摘录),一个节点至少要有 2 个成员任务。新任务来时:先 probe 3 道题,写描述,按 embedding 检索相似任务和节点,优先复用来组合出第一版 harness,再由 Opus 看轨迹做几轮编辑。计划中还有挂在节点上的 designer 侧经验条目。消融计划是 flat 对比两层对比单继承树对比 soft hierarchy。实验设定:冻结的 Qwen3.5-9B 玩文本游戏,关注 Opus 和 Qwen 两边的成本。

**重叠(直说)**
1. **核心动机句几乎一样**:"把通用 harness 机制和环境特定适配分开,让通用部分迁移到新任务"。他们 §1 的"they do not disentangle general harness design from environment-specific adaptation"正是我们 intro 想说的话,而且他们已经用**真代码**实现了,也展示了跨 benchmark 零样本迁移(Table 12)。审稿人会说"这就是 Harmony Harness 的 gen/env 分解"。
2. **按模块名覆盖的两层结构 = 我们消融里的"two-level"甚至"single-inheritance tree"那一档**。他们的 shadowing 是单继承覆盖。
3. **推理时由 LLM 从组件菜单里组合 workflow DAG**,和我们的 `workflow` 节点、"组合第一版 harness"很接近;他们的粒度更细,是每道题重新规划。
4. **promote 操作**:他们的 generalize/Promote(把 benchmark 作用域里的单元提升为通用,并把硬编码事实换成运行时获取)和我们 review 的"提炼共享功能"在操作上相似。
5. **逐字引文证据门**:他们要求 ≥24 字符的逐字引文,并在文件系统上核验(E.1);我们要求 ≥40 字符的逐字摘录或函数名作为成员证据。机制几乎一样,只是用途不同:他们用来核验诊断,我们用来核验节点成员。
6. 都把 harness 当作完整代码包,有组件分类(tools/skills/logic 对比我们的 prompt/memory/control flow/parsing)。

**他们没做的(我们的空间)**
1. **没有多任务库**。每个 run 只在一个 benchmark 上进化,"general"是靠 `decide_scope` 一次 LLM 判断**预测**出来的,没有被 ≥2 个任务的共同使用证实。我们的节点要求 ≥2 个成员任务并附可核验证据,"共享"是被观察到的,不是被预测的。
2. **严格两层**,Σ={gen, env}:没有中间层,没有"一部分任务共享"的节点,没有多父。他们论文里根本不存在"若干个 benchmark 组成一个族、族内共享 workflow"这种结构,因为每次只有一个 benchmark。
3. **不纳入外部 harness**:只用自己 MOEA/D 进化出来的 harness;没有"任意来源 + 质量门"的逐任务纳入流程,也没有任务 profile 和描述、检索。
4. **新任务上没有适配流程**:迁移是零样本的,只加载 general,不做 probe、检索或编辑。我们是"复用优先组合 + 少量编辑"。
5. **领域单一**:只有安全代码生成(3 个 benchmark,目标相同);proposer 和 solver 都是 gemini-3.6-flash,没有"强 designer + 冻结小模型"的设定。
6. **不把 cost 当目标,也不报 proposer 成本**;我们会算 Opus 和 Qwen 两边的 token。
7. 没有设计者侧经验(when/provide/use)和失败版本历史。

**审稿人可能的攻击与应对**
- "通用/特定分解加组合,Harmony 已经做了,还展示了跨 benchmark 迁移。" → 应对:正面承认,并**把它的结构当作我们消融里的 two-level 臂**(gen/env + 同名覆盖)。要用实验证明,在任务数多(训练 5 个游戏族,测试 6 个)且任务间存在部分重叠时,two-level 会丢掉"只在一部分任务间共享"的代码(例如 Wordle/Mastermind/Hangman 共有的约束追踪,对 BabyAI/ALFWorld 没用),而 soft hierarchy 能保留下来。关键在于拿出具体的节点例子,并在 held-out 任务上量出差距。
- "你们的 ≥2 成员证据不过是更严格的 generalize。" → 应对:他们的 generalize 只依据单个环境内"能否在运行时获取",是在一个任务的视角里做判断;我们是跨任务的证据聚合,而且节点可以有多个父节点。可以补一个实验:用他们的 `decide_scope` 规则给我们的组件分 gen/env,和我们按成员证据的分法比较迁移效果。
- "多目标呢?你们只看分数。" → 应对:我们的第二个轴是 cost(Opus 构建 token 和 Qwen 推理 token),而他们完全没报 proposer 成本;可以引用他们 Table 8(编排多花 8% token)说明成本值得报。
- "他们每题动态规划 DAG,比你们每个任务固定一个 workflow 更灵活。" → 应对:目标不同,我们的 workflow 节点是跨任务复用的单位;动态规划可以作为我们 harness 内部的一个 module。若审稿人坚持,可以加一个"按题规划"的对照。
- "单个 benchmark 30 题就够做结论吗?"(反过来也可以用来攻击他们)我们自己的测试集也要注意题数和多次运行,不要犯同样的错。

**结论**:这是目前和我们**动机重叠最多**的一篇:用真代码分出通用部分和环境特定部分,推理时组合,还验证了跨 benchmark 迁移。它是一个 two-level、单 benchmark 进化、靠规则预判通用性的版本,没有多任务库、部分共享、多父 DAG、外部 harness 纳入和新任务适配流程,也不算成本。论文必须引用它,写清楚差异点;它的 gen/env + 同名覆盖结构应该原样实现为我们消融的 two-level 臂(没有发布代码,只能按附录 E/F 自己实现)。我们的卖点要落在"共享是否被 ≥2 个任务的证据证实"和"部分共享结构在多任务 held-out 上的增益"这两条上,不要再说"首次分离通用与特定"。
