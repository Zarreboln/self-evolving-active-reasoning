## 任务

固定 executor 模型 m、任务环境和评测协议,在**每个 benchmark 上各自**优化一个完整可执行 harness(context construction、state management、tool use、termination 及其组合)。目标是式 (2) $h^\star \in \arg\max_h s(h\mid D_v)$,受 N 次 refinement attempt 预算约束;搜索结束后取验证分最高的候选,在不相交的 held-out test set $D_t$ 上报分(§2 "Budgeted Optimization Protocol")。

## 问题

harness 设计空间开放,每个候选都要端到端执行才能评估,代价高。核心问题原文是 "How can we systematically search over complete executable harnesses while making effective use of a limited candidate-evaluation budget?"(§1)。作者认为 Meta-Harness 只沿当前候选迭代,"rather than maintaining a persistent search tree"(§4.1 Baselines),预算分配因此不够系统。

## 方法

- **Code-represented harness**(§3.1):每个候选是一整个代码库,由 coding agent 在文件系统工作区里查看和修改,一次 proposal 可以跨文件协同改动多个机制。
- **Experience archive A**(§3.1):存历史实现、代码修改 $\Delta_n$、验证分、task-level 执行记录、父子关系、相对父节点的分数变化 $q_n-q_{p_n}$。coding agent 按需检索,不必全量放进 context。改进和未改进的 refinement 都写进 A(§3.2 Experience Backpropagation)。
- **Harness Component Library L**(§3.1, 附录 B, Fig. 5):21 个 benchmark-neutral 的 Python 模块,作为**只读快照**提供。coding agent 被要求把采用的代码及其本地依赖**复制**进候选,不能在运行时 import,保证每个候选 self-contained。原文定位:"optional implementation references rather than a fixed template or an exhaustive search space"。
- **MCTS 式父节点选择**(§3.2, 式 3–5, Algorithm 1):候选集 $C_n$ = 分数最高的 K=5 个节点;exploit 项是分数 softmax $\exp(q_i/\tau)$,explore 项是 $(1+d_i)^{-\alpha}$($d_i$=直接子节点数);两者混合 $\pi_n=(1-\varepsilon)P_{exploit}+\varepsilon P_{explore}$,ε=0.35,α=1。τ 自动设定为 shortlist 上验证分的一个标准误,clip 到 [0.005, 0.1](脚注 1),"keeps the policy free of a per-benchmark constant"。
  - 注意:这里所谓 MCTS 只借了 selection/expansion/evaluation/backprop 的名字。没有 rollout,也没有 UCT 式的子树价值回传。"backpropagation" 只是给父节点的 $d_p$ 加 1 并写入 archive,每个节点保留自己直接测得的 $q_i$(§3.2)。
- **树结构**:单父 refinement tree,每个 harness 只有一个父节点。作者在局限里明确说可以扩展成 graph,"so that a candidate can combine mechanisms discovered on separate branches"(§6)。

## 对照问题 a–j

**a. 跨任务共享的是什么?**
**几乎不共享。** 每个 benchmark 各跑一次独立搜索:树、archive 和最终 harness 都只属于这个 benchmark(§2, §4.1 "Each benchmark is split once ... into a validation set used during search")。唯一跨 benchmark 保持不变的,是**作者提供的那份 21 模块 Harness Component Library**(附录 B 称其 "the library used in our experiments",版本标签 "general/v1",并说 "benchmark-neutral")。另外 coding agent(Codex + GPT-5.5)和选择策略的超参数也跨 benchmark 固定。论文没有把某个 benchmark 搜索中得到的任何代码、经验或 archive 带到另一个 benchmark。

**b. 共享库的结构?(关键:21 个模块怎么来的)**
- **来源:论文没有说明是怎么构建的。** 全文找不到 "hand-written"、"distilled"、"curated from"、"extracted from evolved harnesses" 一类说法。可以确定的只有:
  1. 它是**搜索前就存在的固定只读快照**("read-only snapshot",§3.1, 附录 B),搜索过程中**不增长、不更新**。Algorithm 1 里 L 只是 Refine 的输入,搜索新发现的机制(比如 SWE-V 的仓库历史检索)只写进 A,从不写回 L。
  2. 只依赖 Python 标准库,模型调用和工具执行由 host 通过 adapter 注入("model calls and tool execution are supplied by the host through a small adapter interface",附录 B)。
  3. 版本名 "general/v1",带 "guide" 和 "index"(Fig. 5 右上角 "Read-only source · guide · index")。
  从这几点和模块名(react、plan_and_solve、critic_revise、router 都是文献里的经典模式)推断,**大概率是作者事先手写或整理的通用组件**,而不是从 evolved harness 里提炼出来的。但这只是推断,论文没有写。论文也没说它是否参考过这六个 benchmark 上的 harness(如果参考过,就有隐性泄漏风险,见 h)。
- **结构:扁平,只按功能分组**,没有层级、没有成员任务、没有证据字段。Fig. 5 把它分成四列加一行共享支持(数字是该组模块数):
  - **Context(2)**:`context.py`(Observation compaction、State-block rendering、RenderBudget);`skills.py`(Operating rules、On-demand skills、SkillCatalog)
  - **Memory & state(3)**:`memory.py`(Within-task notes、Optional persistence hooks);`evidence.py`(Provenance & pending calls、Configurable stale flags);`requests.py`(Request-item tracking、Heuristic coverage checks)
  - **Control(10)**:`loops/` 5 种形态,`react.py`、`budgeted.py`、`plan_and_solve.py`、`goal_directed.py`、`reflect.py`;`workflows/` 5 种形态,`pipeline.py`、`delegate.py`、`sample_select.py`、`critic_revise.py`、`router.py`
  - **Action(2)**:`actions.py`(Normalized actions、Duplicate & retry tracking、AttemptLog);`tools.py`(Argument-schema checks、Tool / effect heuristics、ToolCatalog)
  - **Shared contracts & optional support(4)**:`loops/base.py`(`run(task, history) → RunResult`、HostAdapter、Budget、RunAudit);`verification.py`(Soft action preconditions,默认 "hold once & re-ask");`self_review.py`(One-call answer review:evidence/coverage/format);`recovery.py`(Failure advice:retry/change/stop)
  - 合计 2+3+10+2+4 = 21,与 "21 indexed modules" 一致。
- 使用方式是 **copy · adapt · compose**:模块之间的关系只有一个隐含约定,即 loops 和 workflows 共享 `run(task, history)` 接口。没有"哪些任务用了哪个模块"的记录,也没有模块之间的父子或组合关系。

**c. Harness 如何分解?**
搜索对象是完整代码库,**不做显式分解**:§2 原话 "The search therefore operates over complete executable harnesses rather than a predefined set of prompts, configurations, or components"。只在两个地方有分解的痕迹:(i) §2/§3.1 用 context construction、state management、control flow、tool use 四类机制来描述可改动的范围;(ii) 组件库按 Context / Memory & state / Control / Action 四种功能角色组织。论文没有把已有 harness 反向拆成模块,也没有统计最终 harness 用了库里哪些模块。**采用率论文没报**:最终选中的 harness 复制了哪几个库模块、复制后改了多少,都没有给出。

**d. Held-out tasks 还是 instances?有没有迁移到没见过的 benchmark?**
**只有同 benchmark 内的 held-out instances**。每个 benchmark 用 seed 42 一次性切分为 validation/test:TAU2 92/186、AppWorld 105/210,其余 100/200(附录 C.1)。**没有任何跨 benchmark 或未见任务族的迁移实验**:没有拿 A benchmark 上搜到的 harness 去跑 B benchmark,也没有拿 A 上的 archive 去初始化 B 的搜索。和"泛化"沾边的只有两处:换起点(从 OpenHands 起步,Table 2)和换 executor(GPT-5.4,Table 4)。但这两处都**在新设定下重新搜索**("we rerun harness search from the same initial harness using this executor",Table 4 标题),所以不算迁移。

**e. 是否测了迁移 / 负迁移?**
没有。没有 harness × benchmark 矩阵,也没有组件 × 任务矩阵。和负效应相关的只有几条单点观察:without library 时 AppWorld/BCB-H 几乎不变(80.63 vs 80.76;31.90 vs 32.50),说明这份通用库对部分 benchmark 基本没用;GPT-5.4 executor 下 WebShop 的 HarnessFlow(71.72)低于 Codex/Hermes/Claude Code/Meta-Harness,论文没有讨论。

**f. 预算、模型、成本**
- Proposer / coding agent:**Codex CLI 0.154.0 + GPT-5.5,最高 reasoning effort**(附录 C.4);Meta-Harness 用同一个。
- Executor(target):**GPT-5.4-mini,medium reasoning**;§4.3 另用 GPT-5.4。辅助模型:TAU2 user simulator 用 GPT-5.2,evaluator 用 GPT-5.5;BC+ grader 用 GPT-5.5。
- 搜索预算:N=15 次候选 attempt,每个候选(含 root)在验证集上执行 R=5 遍;test 同样 5 遍。
- 每任务执行限制见 Table 7(例如 TAU2 200 steps / 1,800 s,SWE-V 250 model calls / 2,400 s)。
- 成本:只报**执行成本**(Table 8,按 GPT-5.4-mini 标价 $0.75/M in、$4.50/M out 计)。**搜索本身的成本(proposer token、验证集 15×5 遍的执行费用、墙钟时间)完全没报**,原文说 "These estimates exclude one-time harness-search costs"(§4.2),§6 只把它定性为 "one-time cost that is amortized"。

**g. Baselines(含 Meta-Harness)与主数字**
见"结果"一节。三类 baseline:Vanilla(各 benchmark 官方参考 agent,也是搜索根节点;Table 5 列了 upstream commit);四个生产级 agent(Claude Code 2.1.272、Codex 0.154.0、OpenHands cloud-1.45.0、Hermes v2026.9.7;Table 6);Meta-Harness(同一初始 harness、同一 coding agent、同一 15 候选预算和同一评测协议)。主数字:69.48 vs Meta-Harness 65.53 vs Vanilla 58.59。
- **一个重要的不明之处**:论文**没有说明 Meta-Harness baseline 能不能访问那份 21 模块组件库**。C.4 只写 "same initial harness, coding agent, and candidate budget"。如果它不能访问,那么 HarnessFlow 相对 Meta-Harness 的 +3.95 里有一部分来自库,而不是来自 MCTS。不过可以从 Table 2 粗略比较:三个 benchmark 上 HarnessFlow without library 平均 63.39,Meta-Harness 在同三项(TAU2 74.62、AppWorld 76.76、BCB-H 30.10)平均 60.49。所以去掉库后,搜索本身仍高出约 2.9(这个数是我按 Table 1/2 算的,论文没给)。
- 没有和 ADAS、AFlow、DarwinX、AutoSaddler、HarnessX 等方法直接对比;AFlow 只在附录 A 里从定性上做了区分(它只搜 workflow 层,proposer 是单次模型调用)。

**h. 泄漏 / 过拟合控制**
- validation/test 一次性固定切分;"The test set is never observed by the optimizer"(§4.1),coding agent "never sees test tasks"。
- 所有方法共用一个固定的 runtime 快照,运行在网络隔离的 sandbox 里,唯一出口是 model gateway(§4.1, C.3)。
- 最终按验证分 argmax 选候选。验证集只有约 100 题 ×5 遍,15 个候选里取最大值,存在 winner's curse:验证 best-so-far 74.2 对应 test 69.48,差约 4.7。论文没有讨论这个差距,也没有另设 selection split。
- 组件库是否参考过这六个 benchmark 写成,论文没说明。"benchmark-neutral" 只是自称,没有给出构建过程或审计。
- 没有讨论 reward hacking,也没有讨论 LLM grader(TAU2 evaluator、BC+ grader 都是 GPT-5.5)被候选 harness 针对的风险。
- 每个方法只搜索一次(single search run);±std 只反映 5 次执行的随机性,不反映搜索本身的方差。

**i. 代码 / 数据**
未发布,只承诺 "will be released"(Reproducibility Statement)。组件库源码、搜索树、archive 和最终 harness 都没有公开。GitHub 上的同名仓库都与本文无关。

**j. 自述局限与未来工作**(§6,只有一段)
(1) 依赖自动 grader,只适用于有自动评分的任务;(2) 搜索要消耗评估计算,这是一次性成本,可以摊销,但限制了可行的预算规模;(3) 树结构使每个 harness 只有一个父节点,未来想扩展成 graph,让候选能"combine mechanisms discovered on separate branches"。**没有提到**跨 benchmark 迁移、组件库的构建与更新、搜索方差或搜索成本。

## 与我们的区别

我们的方法:把完整 agent harness(冻结 LLM 外的 prompts / memory / control flow / parsing 代码)分解成新任务可复用的 soft hierarchy。harness 来源不限(Meta-Harness 进化出来的、人写的),先过质量门(要明显超过 base agent),再逐任务摄入。Opus 根据 3 条 base-agent trace 写出任务描述、能力和 profile,再写 harness 描述;然后做 review,把共享功能提炼成 `module` / `workflow` 节点。节点构成多父 DAG,每个节点有真代码、描述、父节点和成员任务,每个成员都要带可核对的证据(函数名或 ≥40 字原文摘录),每个节点至少 2 个成员任务。新任务:probe 3 题 → 写描述 → 按 embedding 检索相似任务和节点 → 优先复用,组合出第一版 harness → Opus 看 trace 做几次 edit。计划扩展:节点上挂 designer 侧经验条目(when/provide/use),证据来自含失败尝试的版本历史。消融:flat / 两层 / 单继承树 / soft hierarchy。设定:冻结 Qwen3.5-9B 玩文本游戏,训练任务和测试任务是不同的 game。

**重叠(直说)**
1. **"给 coding agent 一个可复用 harness 代码库,让它在写新 harness 时 copy/adapt/compose"**:这跟我们新任务阶段的"检索节点 → 优先复用 → 组合第一版 harness"在机制上是同一件事。审稿人会说"HarnessFlow 已经有 reusable component library,而且做了 with/without library 消融"。他们的库同样是代码,同样按 context / memory / control / action 分功能,同样有 loops(≈我们的 module)和 workflows(≈我们的 workflow)。连 `workflow` 这个词都撞了。
2. 都以 Meta-Harness 为直接 baseline,都是冻结 executor + 强 coding agent 改整个代码库,都靠 trace 和 archive 驱动 edit。我们新任务阶段的"几次 Opus edit"就是一个小预算的 Meta-Harness/HarnessFlow 内循环。
3. 他们 §6 的 future work("search over a graph, so that a candidate can combine mechanisms discovered on separate branches")和我们的多父 DAG、"组合不同来源的机制"在表述上接近,容易被拿来说"已有人提出"。不过他们指的是候选谱系图,不是共享库的结构。
4. 他们 with/without library 的消融(Table 2)相当于我们"有库 vs 无库"那一档的先例,而且结果不算强(+1.64,主要来自 TAU2)。审稿人可能会拿这个数质疑"共享库收益本来就小"。

**他们没做的(我们的空间)**
1. **库从哪来、怎么长**:他们的库是固定、来源不明(很可能手写)的只读快照,搜索中发现的机制(SWE-V 的 repo-history retrieval、TAU2 的 state-changing action review)**从不回流进库**。我们的库是**从多个 harness 里自动提炼出来的**,每个节点带成员任务和可核对证据,而且逐任务增长。这是最核心的区别。
2. **跨任务**:他们每个 benchmark 独立搜索,**没有任何跨 benchmark 迁移**,held-out 只是同 benchmark 内的实例(附录 C.1)。我们评测的是没见过的任务(Mastermind、Minesweeper、ALFWorld 等新游戏)。
3. **结构**:他们的库是扁平的 21 个模块,只按功能分组;没有成员任务,没有层级,没有多父。我们的多父 DAG、"节点需 ≥2 成员任务"、证据约束,以及 flat / 两层 / 单树 / soft 的消融,他们都没有。
4. **库的使用不可观测**:他们没报最终 harness 采用了哪些模块、改了多少。我们的节点-成员证据天然可以回答"复用了什么"。
5. **来源无关的摄入和质量门**:他们只在自己的搜索树里工作。我们可以吸收人写的、Meta-Harness 进化出来的等任意来源的 harness,并设质量门。
6. **冷启动**:他们从 benchmark 官方 agent 起步,用 15×5 遍验证集预算。我们的卖点是新任务只 probe 3 题加少量 edit,预算小一个数量级。他们自己也不报搜索成本。
7. **小开源 executor**:他们用 GPT-5.4-mini / GPT-5.4,我们用冻结的 Qwen3.5-9B。
8. **设计者经验**:他们的 archive 记录了失败的 refinement 和 $q_n-q_{p_n}$,但只在同一次搜索内部给 coding agent 看,不提炼、不跨任务。我们计划把含失败尝试的版本历史提炼成挂在节点上的 when/provide/use 经验条目。

**审稿人可能的攻击与应对**
- "复用组件库已被 HarnessFlow 做过,你们只是把库换成 DAG。" 应对:正面区分**库是给定的**(HarnessFlow,固定只读、来源未说明)和**库是从 harness 自动提炼、可增长、带证据的**(我们)。最好加一个 baseline:把 HarnessFlow 的 21 模块 general 库(若发布;否则用我们按其 Fig. 5 重写的同功能手写库)作为 flat 库喂给同一个新任务流程,和我们提炼出的 soft hierarchy 比。这样既回答了"手写通用库够不够",也把它变成我们 flat 消融的一档。
- "共享库收益很小(他们 +1.64,AppWorld/BCB-H 几乎为 0)。" 应对:他们的库和任务无关,而且只在单 benchmark 的长搜索(15 候选)里使用,库的作用被搜索稀释了。我们的设定是**低预算冷启动的新任务**,库的价值应主要体现在第一版 harness 和 adaptation curve 的前几步。必须报"第 0 次 edit 时的分数"以及小预算曲线,才能展示这一点。
- "直接对新任务跑 HarnessFlow / Meta-Harness(给足预算)就行了,为什么要库?" 应对:报同预算比较(我们 3 probe + k 次 edit vs Meta-Harness/HarnessFlow 用 k 个候选),同时报达到同等分数所需的预算;并承认在预算无限的情况下,单任务搜索可能追平。
- "多父 DAG 他们也列为 future work。" 应对:他们指的是**候选谱系**的多父(跨分支合并机制),不是**共享知识**的多父归属。两者正交,可以引用作为"多父结构有价值"的旁证。
- "你们的提炼也是 LLM 写的,怎么保证节点真实被多任务共享?" 应对:这正是 ≥2 成员任务 + 可核对证据(函数名 / ≥40 字原文摘录)的作用,HarnessFlow 的库没有任何这类可核查性。

**结论**
HarnessFlow 是**单 benchmark 内的搜索算法论文**(MCTS 父节点选择 + Meta-Harness 式全代码 refinement),跨任务学习不是它的主题。和我们真正撞车的只有一处:**它给 coding agent 提供了一个可复用的 harness 代码组件库,并做了有/无库的消融**。但这个库是固定、扁平、来源未说明(很可能手写)的 21 个通用模块,不会从搜索中增长,没有成员任务或证据,也从未用于跨 benchmark 迁移。我们的核心贡献(从多来源 harness 自动提炼带证据的 soft hierarchy,并在未见任务上低预算复用)它没有覆盖。论文需要引用它,在 related work 里明确"given library vs distilled library"的区别,最好再把它的 21 模块 flat 库(或同功能复刻)作为 flat 消融档里的一个 baseline。它的 MCTS 选择可以视为我们新任务 edit 阶段可替换的内循环,不构成竞争。
